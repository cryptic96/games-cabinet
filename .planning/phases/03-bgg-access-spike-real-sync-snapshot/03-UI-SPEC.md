# Phase 3 — UI Design Contract

> Visual and interaction contract for the real-data sync surfaces: the sync status line, the stale note, the "being filled" state, expansions without a known base game, live in-place redraw, the BGG credit in the footer and the local-only sample switcher. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Reading guide.** This phase **extends** the approved Phase 2 contract (`02-UI-SPEC.md`). It does not re-decide anything that file locks: the wood palette, the 60/30/10 split, the accent reserved list, the type scale (3 fixed sizes, 2 weights), the spacing scale, the focus ring, the strict-CSP renderer rules, the cabinet furniture and every in-cabinet rule. Where this file is silent, Phase 2 applies. Values tagged **FIXED** are not for tuning; values tagged **STARTING VALUE** may be tuned in review.

## Page Chrome Contract (Index page, additions to Phase 2)

Page order in `header`: `h1`, **sync block**, optional exact-time line, **own-press note**, **stale note**, dev-only switcher. `main` follows with the empty-state message (when applicable) above `#cabinet`. `footer` closes the page.

### Sync block (D-06, D-07, D-08)

Sits directly under the title, scrolls away with the header. It is not sticky and not in the footer.

```
Games Cabinet
Synced 12 minutes ago   [ Sync now ]
(exact time, only when toggled)
(own-press note, only after pressing)
(stale note, only when stale or held back)
```

| Element | Contract |
|---------|----------|
| Container `.sync` | flex row, `flex-wrap: wrap`, `align-items: center`, gap 8px (row) and 16px (column), `min-height: 44px`. Margin-top 4px under the `h1` (the existing `h1` margin-bottom 4px). The 44px row height is reserved by CSS so unhiding the button after load never shifts the layout |
| Relative time | a `<button type="button" class="sync-time">` containing a `<time datetime="{UTC ISO}">` whose text is "Synced 12 minutes ago". Body style, `--wall-text`, no border, no background, `padding: 0`, `min-height: 44px`, `text-decoration: underline dotted`, `cursor: pointer`, `white-space: nowrap`. `title` = the exact local date and time (desktop hover). `aria-expanded` reflects the exact-time line. Pressing toggles the exact-time line (D-08: tap on touch devices) |
| "Sync now" button | `<button type="button" class="sync-button" aria-disabled="false">`. Label style (14px, 400), `min-height: 44px`, `padding: 8px 16px`, 1px solid `--chrome-line`, radius 4px, transparent background, colour `--wall-text`. Hover (pointer devices only): underline, same as the sample links. No pressed style. `hidden` in the server markup and revealed by script, so a visitor without JavaScript never sees a dead button |
| Exact-time line `.sync-exact` | Label style, `--wall-text`, margin-top 8px, one line that wraps. Text: "Last synced {exact local date and time}" (see Copywriting for the format). Hidden until the relative-time button is pressed; pressing again hides it. Not a live region. Updates in place when a newer sync lands while it is open |
| Own-press note `#sync-note` | `<p role="status" aria-atomic="true">`, present in the DOM from the first render (empty), Body style, `--wall-text`, margin-top 8px, `max-width: 40rem`. See "Live region rules" |
| Stale note `.sync-stale` | `<p>` (no live role), Body style, `--wall-text`, margin-top 8px, `max-width: 40rem`, `border-inline-start: 4px solid var(--chrome-line)`, `padding-inline-start: 8px`. Hidden unless the stale or held-back condition holds (see Copywriting) |

The sync block and both notes are `max-width: 40rem` so a long note wraps like body text and is never truncated. Nothing in the block is truncated at any width from 320px; it wraps (the two pressables drop onto separate rows when they do not fit).

**Dot separator (deliberate deviation from the quoted line).** The example line "Synced 12 minutes ago · Sync now" uses a centred dot. The outlined button is its own visual separator, and a dot would dangle at the end of a wrapped row on a phone. The contract is therefore **no dot character in the DOM or the CSS**. If the owner wants the dot back after seeing it, add it only as CSS generated content with empty alternative text, hidden on phone.

### Sync button states (FIXED set; precedence: running, then cooldown, then idle)

| State | Button text | `aria-disabled` | Note (own press only) | Trigger |
|-------|-------------|-----------------|-----------------------|---------|
| Idle, never synced | `Sync now` | false | none | no successful sync yet and no cooldown |
| Idle | `Sync now` | false | none | cooldown over, nothing running |
| Running | `Syncing...` | true | none until it finishes | a sync is running, whoever started it (hourly timer, another visitor, this visitor). The button reads the same for everyone |
| Cooldown | `Sync again in 9:42` | true | none | cooldown window active after any manual sync, success or failure |
| Cooldown after failure | `Sync again in 9:42` | true | "BGG didn't respond..." (see Copywriting) | the visitor's own press ended in failure; the countdown still runs |

- The button is **never** natively `disabled`; `aria-disabled="true"` keeps it focusable so the reason can be given when it is pressed.
- **Pressing while not pressable sends no request.** While running it shows the note "A sync is already running."; during cooldown it shows "You can sync again in {n} minutes." (computed once at press time, so it does not tick). Both go through the live note.
- **If the press request itself fails** (offline, no answer from the site), the note shows "Couldn't start the sync...", **no cooldown starts** (the server never received the press) and the button stays `Sync now`.
- **If the page's state was stale** and the server answers that a sync is already running or the cooldown is active, the page adopts the server's state (button and countdown) and shows the matching note above. A server refusal is never shown as an error.
- **Countdown:** format `m:ss` (`9:42`, `0:07`), driven by the cooldown end timestamp (UTC) minus the server-adjusted clock; the page keeps an offset from the server time in the status response so a wrong visitor clock does not mis-state it. It ticks once a second **only while the tab is visible** and the cooldown is active, and stops cleanly at zero. At zero the label returns to `Sync now`. **FIXED.**
- **Relative time refresh:** the "Synced ... ago" text is recomputed every 30 seconds while the tab is visible, on becoming visible again, and whenever a broadcast or status response arrives. **STARTING VALUE** for the 30 seconds.

### Live region rules (screen readers, FIXED)

The page has exactly **one** live region, `#sync-note` (`role="status"`, polite). Rules:

1. **Only a visitor's own press writes to it.** The hourly sync, another visitor's sync and any broadcast change the visible button, the relative time and the cabinet silently. A timer-driven sync never speaks.
2. **Nothing that ticks is ever inside a live region or announced.** The countdown and the relative time are plain text. The button's accessible name during cooldown is set with `aria-label="Sync again in 9 minutes"` (whole minutes, rounded up; "Sync again in less than a minute" in the last minute) and rewritten **only when that minute value changes**, never per second. The visible per-second digits are not exposed as separate text. When the cooldown ends, `aria-label` is removed.
3. The note is cleared (set to empty) when the cooldown ends, which announces nothing.
4. The stale note and the exact-time line are not live regions. They are discoverable by reading order.
5. The cabinet redraw announces nothing (D-10).
6. At most one message is announced per press cycle: when the press is accepted nothing is announced (the button text changes to "Syncing..."), and the outcome is announced once when the sync ends.

### Header text on the first render

The server renders the relative-time text, the stale note (when it applies) and the button's initial state from the snapshot and sync state, using UTC for any date, and the script rewrites the dates in the visitor's local time on load. The server-rendered text is the no-flash starting point; the script does not need a separate request for first paint.

## Empty state: the cabinet is being filled (D-16, SYNC-05)

Shown while **no sync has ever succeeded**. It is not tied to the item count: a first sync that succeeds with an owner who really has no games shows the bare cabinet with no message.

- A normal 200 page, never an error, never a status code other than 200.
- In `main`, **above** `#cabinet`, a block `.cabinet-message.cabinet-filling`: a heading line (Body, weight 600) and a body line (Body, weight 400), centred, `--wall-text`, `max-width: 40rem`, margin-bottom 24px (lg), margin-inline auto. Same two-line pattern as the load-error message. No icon, no spinner, no illustration, no animation.
- Below it, the Phase 2 minimum cabinet exactly as it is: one section, bare planked wood, **no text, no props, no icons inside it**. The layout endpoint answers 200 with the empty collection's layout; the page draws it like any other.
- The sync block still shows: `Not synced yet` plus the `Sync now` button, so a visitor can start the first sync (SYNC-02 still allows it).
- When the first sync finishes, the quiet redraw replaces the empty cabinet and the message block is removed in the same step (no announcement for passive visitors; see "Live region rules").
- With JavaScript off, the existing no-script message stays; the "being filled" block is server-rendered so it still shows.
- Replaces the retired "The cabinet is being built. Check back soon to browse the collection." line, which is removed for good (the deployed site never shows the prototype state any more).

## Stale and held-back notes (D-11, D-12, D-13, SYNC-04)

| Condition | Shown |
|-----------|-------|
| Last good sync is 3 hours old or older (**STARTING VALUE**, 3 hours), no held-back result | the stale note, "recent syncs" variant |
| A suspicious result is currently held back (empty, or shrunk by more than half), regardless of age | the stale note, "held back" variant |
| A single failed hourly run, last good sync under 3 hours old, nothing held back | **nothing** (stays quiet) |
| Never synced | no stale note; the "being filled" state covers it |

- Both variants start with the same words, "Showing the last sync from {exact local date and time}.", so the note reads as the note SYNC-04 asks for. Exact copy in the Copywriting Contract.
- The note disappears as soon as a fresh good sync lands (no message needed).
- The note is persistent and calm: no colour change, no icon, no weight change. The rule on its left edge is its only marker. It is not a live region.
- A held-back result is never shown on the page as a number of games or a count; only the sentence.

## Live update and redraw (D-09, D-10)

The page receives server broadcasts (sync started, sync finished or failed, collection changed with the snapshot version, cooldown state) and fetches the current status once on every connect and reconnect.

**Quiet in-place redraw (FIXED):**

- On a collection-changed broadcast whose snapshot version differs from the one on screen, the page fetches the layout for the **current profile** and swaps it in with one `replaceChildren`.
- **No loading line, no spinner, no crossfade, no highlight of new or moved boxes, no scroll jump.** The old cabinet stays on screen until the new one is ready, and the swap is a single step. Nothing is announced.
- The existing loading state (the "Loading the cabinet..." line) and the load-error state (with "Try again") stay as they are for the **first** load and for a profile change. They are never used for a live redraw.
- **A failed quiet redraw is silent:** the old cabinet stays, no error appears, and the page tries again on the next broadcast or reconnect.
- A newer load supersedes an older one in flight (the existing superseded-load protection is reused).
- If the same snapshot version is already on screen, nothing is fetched and nothing is redrawn.
- **Keyboard position is kept:** if a box had keyboard focus when the swap happens, focus goes to the box with the same `data-entry-id` after the swap when that box still exists; otherwise focus is left on `body`.
- A hidden tab does not redraw. It remembers that the collection changed and redraws once, when it becomes visible. **STARTING VALUE** (saves battery and memory on a phone).
- The swap is not wrapped in any transition, so `prefers-reduced-motion` needs no special case.

**Connection loss (FIXED: invisible):**

- The page never shows a "connection lost" or "reconnecting" banner. The status line keeps working from the timestamps it already has; the cooldown countdown and relative time are computed locally.
- Reconnect is automatic with increasing delays (**STARTING VALUE**: immediately, 2 s, 10 s, 30 s, then every 60 s without giving up). On every reconnect, and when the tab becomes visible or the browser reports it is back online, the page fetches status once.
- While a sync **this page started** is running and the connection is down, the page checks status every 5 seconds until it ends, up to 10 minutes, so "Syncing..." can never stay stuck.
- While running is shown for longer than the longest plausible sync with no update, the next status fetch corrects it; the button never stays in "Syncing..." for more than the status poll's reach.

## Real-game rendering changes (D-14, D-15, D-19)

### Expansion without a known base game (D-15)

Until base games are paired, every owned expansion shows as an orphan expansion box with the existing look (flat box, two lines) but **without a base-game title**.

| Part | Contract |
|------|----------|
| Look | exactly the Phase 2 orphan expansion box (palette tone, flat box, minimum rendered height 36px, 12px floor); only the second line differs |
| Second line | `Expansion` (weight 400, 12px, the existing sub-label style, one line, ellipsis). It replaces "Expansion for {base game title}" **only** when no base title is known |
| Accessible name and `title` | `{title}, expansion` (comma, lower-case "expansion") instead of the title alone |
| When a base title is known | unchanged ("Expansion for {base}", name "{title}, expansion for {base}"). This is how the label upgrades itself when base games are paired later, with no renderer change |
| Small collections | an expansion that would be drawn as a face-out cover (few-games look) also shows the `Expansion` line, so it is never mistaken for a base game |
| Data | the layout data must tell the renderer that a placement is an expansion even when it has no base title (for example a flag on the placement), because today "no base title" currently means "not an expansion line" |
| Blank title | still `Untitled game`, name `Untitled game, expansion` |

They sit in the first cubby with room (the engine's existing rule); nothing in the renderer positions them.

### Real titles and sizes (D-14)

- The renderer draws whatever millimetre rectangle the layout gives it. Real owned-version dimensions and the single default size are an engine concern; nothing visual is added or flagged for a game that uses the default size (Phase 2: "no visual flag").
- The cabinet reflows when real sizes arrive later; the redraw rule above makes that quiet.
- All title text keeps the Phase 2 rules: `textContent` only, `dir="auto"`, 12px floor, truncation backstop, full title in `aria-label` and `title`.

### One box per copy (D-19)

- Two owned copies of the same game render as **two separate buttons**, like two boxes on a shelf. Nothing merges, hides or labels them (no "copy 2", no count badge).
- Every placement button carries `data-entry-id` (the collection entry id) next to the existing `data-game-id` (the BGG id). Anything that must be unique per box (redraw focus restore, future detail, test hooks) uses `data-entry-id`.
- Both copies keep the same accessible name. That is acceptable: they are indistinguishable by design, like two physical boxes.

## Copywriting Contract

English only; all strings live in the existing single strings module (`copy.js`) or in the server-rendered markup, so the later language work touches few places. Plain dots (`...`), never the ellipsis character. Plural follows the count.

| Element | Copy |
|---------|------|
| Primary CTA | `Sync now` |
| Relative time, under a minute | `Synced just now` |
| Relative time | `Synced 1 minute ago`, `Synced 12 minutes ago`, `Synced 1 hour ago`, `Synced 3 hours ago`, `Synced yesterday`, `Synced 3 days ago` (rule: under 60 s "just now"; under 60 min whole minutes; under 48 h whole hours rounded down; beyond that whole days; a time in the future clamps to "just now"). Build with `Intl.RelativeTimeFormat('en', { numeric: 'auto' })` |
| Never synced | `Not synced yet` |
| Button, idle | `Sync now` |
| Button, running | `Syncing...` |
| Button, cooldown | `Sync again in {m:ss}` (`Sync again in 9:42`) |
| Button accessible name, cooldown | `Sync again in {n} minutes` / `Sync again in 1 minute` / `Sync again in less than a minute` |
| Exact time line | `Last synced {exact}` where `{exact}` is `Intl.DateTimeFormat('en-NL', { day: 'numeric', month: 'long', year: 'numeric', hour: '2-digit', minute: '2-digit', timeZoneName: 'short' })` in the visitor's own time zone, for example `6 October 2026 at 14:32 CEST`. **Owner decision:** English words with the Dutch date order and 24-hour clock (`en-NL`, "English as used in the Netherlands"), not `nl-NL`, which would put Dutch words ("oktober", "om") inside the English line. The same string is the `title` of the relative-time button. The locale is a single constant; the language work later swaps it for `nl-NL` in the Dutch UI |
| Own press, accepted | none (the button itself changes) |
| Own press, finished with changes | `Collection updated. BGG can take a few minutes to show recent edits.` |
| Own press, finished without changes | `No changes found. BGG can take a few minutes to show recent edits.` |
| Own press, BGG failed (any failure category: unavailable, throttled, timeout, bad answer, configuration) | `BGG didn't respond. The last collection is still showing.` |

## Interaction, Motion and Accessibility Baseline (additions)

- **Motion:** none added. There is no spinner, no pulsing, no progress bar, no transition on state changes, no animation on redraw. The only motion in the app is still the Phase 2 hover lift, which `prefers-reduced-motion: reduce` already removes. "Syncing..." is words only.
- **Keyboard:** new tab stops, in DOM order: the relative-time button, the "Sync now" button, then the cabinet's placements, then the credit link. Both buttons work with Enter and Space (native `<button>`). The credit link works with Enter. Every focusable element shows the global accent focus ring; none is clipped. Focus stays on the button when its text changes; it is never moved by a state change.
- **Screen readers:** landmarks unchanged (`header`, `main`, `footer`). The sync block is a plain `div` (no landmark). One live region (`#sync-note`); rules in "Live region rules". The relative-time button exposes `aria-expanded` and `aria-controls` for the exact-time line. The "Sync now" button exposes `aria-disabled`. The logo has `alt="Powered by BGG"` and sits inside a link, so the link's name is that text.
- **Touch and phone (320px up):** both pressables are at least 44px tall; the row wraps onto two lines instead of shrinking; the notes wrap; the footer credit wraps below the version text; no horizontal scroll at any width from 320px (Phase 2 rule still holds).
- **Colour is never the only carrier of meaning:** the not-pressable button also changes its words, its dashed border and `aria-disabled`; the stale note also has a sentence starting "Showing the last sync from".
- **Contrast (FIXED):** every new text is at least 4.5:1 on the backdrop (lowest: `--chrome-muted` at about 6.3:1); the button border and the stale-note rule at least 3:1 (about 5.1:1).
- **Strict CSP (FIXED):** the page and the live connection must work with `default-src 'self'` and no CSP violation in the browser console, in every supported browser. If a browser blocks the same-origin live connection under the current policy, the fix is an explicit same-origin connect rule in the policy, never a looser policy. An integration test still fails on `style=` attributes and inline script bodies. JavaScript comments follow the repository rule (`/** ... */` doc blocks only), including in any new module; the copied third-party client script is handled as the live-update plan decides, not by editing this contract.
- **BGG text:** `textContent` only, everywhere, including titles in notes if any ever appear (none do in this phase).

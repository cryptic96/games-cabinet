# Plan 05-03: Synced cards stay fresh

## Phase Goal

ROADMAP goal (not yet in user-story form; flagged, see `/gsd mvp-phase 5`): "A visitor can tap any box, watch it slide out of the shelf, and read everything needed to pick it for game night in English or Dutch, by touch, mouse, keyboard or screen reader."

<objective>
Close the data-model trap the research found: the collection version only hashes what the cabinet draws, and the sync replaces the in-memory view only when that version changes, so a details-only change would leave stale cards until restart (research Pitfall 1, Open Question 2: fold the card fields into the version). Also extract the shared 304 helper both data routes use, and add the cards route to the CSP test list.

Purpose: the card the visitor reads matches the latest sync (D-09 "cached per collection version").
Output: a card-aware `SnapshotMapper.Version` overload, `EntityTags.MatchesIfNoneMatch`, tests.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-03-01 | Tampering | `EntityTags.MatchesIfNoneMatch` | low | mitigate | Parsed by `GetTypedHeaders().IfNoneMatch` (malformed values ignored), compared, never echoed |
| T-05-03-02 | Information disclosure | stale cards after a sync | low | mitigate | Card-visible fields are part of the version; tests prove details-only changes give a new version |
| T-05-03-03 | Denial of service | version hashing cost | low | accept | One SHA-256 over a few hundred short lines per sync commit; no per-request cost |

# Plan 05-11: The box slides out of the shelf, or simply fades for those who prefer less motion

## Phase Goal

ROADMAP goal (not yet in user-story form; flagged, see `/gsd mvp-phase 5`): "A visitor can tap any box, watch it slide out of the shelf, and read everything needed to pick it for game night in English or Dutch, by touch, mouse, keyboard or screen reader."

<objective>
Turn opening and closing into the pull-out the owner wants: lift, turn, become the card, with the slot left empty behind the dim (D-01, D-02), a plain fade where the browser or the situation cannot fly the box, and a short cross-fade with a highlighted box for visitors who prefer reduced motion (D-08, DET-03).

Purpose: DET-01's animation and DET-03.
Output: the View Transition choreography in `detail.js` and `card.css`, pure path decisions in `card-flow.js`, browser tests that observe the animations and their absence.
</objective>

## Flagged assumptions (spec-less edge probe)

- **DET-01, edge category unclassified (unresolved, flagged):** assumed riskiest edge: a tap arriving while a quiet redraw is replacing the cabinet's DOM, so the source box is detached between `pointerdown` and the transition. Planner assumption: `detail.js` re-finds the box by entry id and kind at transition start and falls back to the plain fade when it is gone. Not proven by a probe; checked in the review round.
- **DET-03, edge category unclassified (unresolved, flagged):** assumed edge: the visitor changes the reduced-motion setting while a card is open. Planner assumption: the preference is read at every tap and at every close, so a close uses whatever the current setting is. Not proven by a probe.
- **Research assumption A7:** Firefox 144 and Safari 18 handle a named element inside a modal dialog and `showModal()` inside the update callback like Chromium; if not, the plain fade is acceptable and the owner checks on devices.

# Plan 05-08: The cabinet is one tab stop with arrow keys

## Phase Goal

ROADMAP goal (not yet in user-story form; flagged, see `/gsd mvp-phase 5`): "A visitor can tap any box, watch it slide out of the shelf, and read everything needed to pick it for game night in English or Dutch, by touch, mouse, keyboard or screen reader."

<objective>
A keyboard-only visitor tabs into the cabinet once, moves between boxes with the arrow keys, Home and End, and opens any card with Enter or Space; focus comes back to the box when the card closes (D-17). Closes the folded accessibility todo.

Purpose: A11Y-01; today every box is its own tab stop, hundreds for a big collection.
Output: `keys.js` (pure spatial rule and DOM roving controller), `data-shelf` in the renderer, the cabinet group label and hint, node and browser tests.
</objective>

## Flagged assumptions (spec-less edge probe)

- **A11Y-01, edge category unclassified (unresolved, flagged):** the probe could not classify an edge for "keyboard users move through the games and open any card". Planner assumption carried forward, not verified by a probe: the riskiest unclassified edge is a box that is laid out but has zero size or is fully clipped (for example a stacked layer hidden behind another); `nextBox` treats every `.placement` rectangle as reachable and never skips zero-area boxes, so such a box is still focusable and scrolled into view. Confirm in the review round's keyboard walk.
- **Research assumption A9:** a `role="group"` of buttons with a roving tabindex is acceptable for screen-reader users because they use the A to Z list in browse mode; checked in the manual screen-reader spot check.

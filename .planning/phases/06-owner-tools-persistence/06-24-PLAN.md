Output: the restore check, the restore write, the restore panel, tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Uploaded file to the server | An arbitrary file becomes candidate owner data |
| Restored data to public pages | Location names and choices become public |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-24-01 | Denial of service | huge or deeply nested uploads | high | mitigate | 3 MB request cap (413), 2 MB rule, `MaxDepth = 16`, count limits; one bounded read |
| T-06-24-02 | Tampering | hostile file content (names, links, references) | high | mitigate | Strict deserialisation, name rules incl. control and bidi characters, link policy, reference checks; all-or-nothing |
| T-06-24-03 | Tampering / data loss | restore replacing data by mistake | high | mitigate | Preview with a side-by-side table and a destructive confirm; current data (even unreadable bytes) kept as an earlier version first |
| T-06-24-04 | Tampering (CSRF) | check and restore posts | high | mitigate | Antiforgery on every post |
| T-06-24-05 | Information disclosure (SSRF) | links in a restored file fetched again | medium | mitigate | Links checked by policy at restore; the worker fetches through the same capped token-less client |
</threat_model>

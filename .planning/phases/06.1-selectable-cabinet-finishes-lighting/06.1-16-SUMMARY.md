# Phase 06.1 Plan 16: Live switch - open pages follow the owner's new look within seconds Summary

A look published on the owner's Settings page reaches every open public page within about 3 seconds through the existing live channel: the status carries the look, the notifier announces real look changes once, and a new module applies it with a 250 ms root cross-fade, a lights-only shortcut, a logo swap and a late load of the lamp script, while an open card stays open.

## What was built

- **Status (`CabinetStatus.cs`):** `LookStatus(Design, Wood, Backs, Lights, Depth, LightWall)` with `LookStatus.From` (normalises, so only allow-listed values leave the server) and a trailing `Look` on `CabinetStatus`. `SyncStatusService` gained `SiteLook? look = null`.
- **Notifier:** the dedupe key is now collection version plus look; quiet period (3 s) and ceiling (15 s) are unchanged. A look-only change announces once, a change and back announces nothing, a failed publish is retried on the next change.
- **`look-switch.js`:** `applyLookStatus(status, root)` ignores a status without a usable look (type, length checks) and one older than the newest seen; does nothing when all five values match; lights-only sets the attributes at once; anything else runs inside `document.startViewTransition` with `data-look-switch` on the root (removed when the transition finishes, update runs exactly once whether or not the transition does); reduced motion or no transition support applies at once. It swaps the footer logo from `data-logo-light` / `data-logo-dark`, loads the lamp script from the `cabinet-evening-script` meta address when lights turn on and `window.cabinetEvening` is missing, and reads the layout between writing the attributes and lighting the lamp so the light layer fades instead of appearing.
- **`cabinet.js`:** the live status fan-out calls `applyLookStatus` and then `sync.applyStatus` (pushed and fetched statuses).
- **`card.css`:** `--look-fade: 250ms` and `html[data-look-switch]::view-transition-group(root)` (more specific than, and unlayered like, the 350 ms root rule).
- **Tests:** notifier (4 new), status shape (default look; exactly the five values plus `lightWall`; no location, id or change text anywhere), 11 node tests for `applyLookStatus`, and `LiveLookTests` (5 browser tests: one cross-fade with the card still open, lamp script requested once and loaded before the attributes change with the layer at opacity under 0.5 at the moment it is lit, logo to the dark file and back with the same alt and size, reduced motion with no transition, blocked channel followed by catch-up and by reload).

### Orchestrator hookup note (plan 15 not merged in this base)

`look-switch.js` imports the lamp module as a namespace and calls `lamp.followClock?.(document)` after lighting whenever the new lights are not off, and removes `data-evening` when lights go off (`refreshLamp` already drops `data-lit`). Against this base `followClock` does not exist, so the call is a no-op. After both plans merge nothing further should be needed: a switch from Off to Evenings or On loads the head script from the meta address, applies the look, calls `refreshLamp`, then `followClock`. Things for the orchestrator to check after the merge: (a) the late-loaded head script runs while `data-lights` is still `off`, so it will not set `data-evening` itself; `followClock` must set it (and light the lamp) on its first call, which the contract described says it does; (b) the node tests' fake `look.js` (copied from the folder) will then contain `followClock` and the existing `look-switch` tests, which use a fake root without `ownerDocument.querySelector` for `.sync`, must still give it a document that `followClock` can use, or `followClock` must tolerate the fake; run `node --test build/tests/*.test.mjs` and `LiveLookTests` after merging.

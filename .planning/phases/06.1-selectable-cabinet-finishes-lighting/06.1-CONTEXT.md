# Phase 6.1: Selectable Cabinet Finishes & Lighting - Context

**Gathered:** 2026-10-13
**Status:** Ready for planning

<domain>
## Phase Boundary

From the owner pages, the owner sets the cabinet's look for every visitor:
- a **design** (the build) and a **wood** (the colour), in any combination;
- the wall that comes with the wood;
- an optional **painted backs** extra;
- cubby **lights** (Off, Always on, or Evenings only by the visitor's clock);
- a cubby **depth** (Flat, Shaded or Deep).

The owner tries combinations in a preview on the settings page and publishes them with one press. Open pages follow live.

The phase starts with a mock-up round on the real cabinet, built from the recovered earlier mock-ups. Nothing is built before the owner approves the round.

Also in this phase, folded from todos:
- balancing uneven desktop sections in the layout engine;
- the owner's "Check link" failing while the background link worker is busy.

**Not in this phase:**
- a visitor-side finish switcher (the owner's choice is site-wide);
- filters and location cabinets (Phase 7);
- go-public (Phase 8).

**This changes earlier decisions.** The owner changed the earlier "seven fixed finishes" (Phase 6 context, D-31) into designs × woods, and the two light switches (D-33) into one three-way control. Everything else recorded for this phase in the Phase 6 context still holds: D-30, D-32, D-34 (no location data, the fade, reduced motion), D-35 and D-36.

## Implementation Decisions

The UI decisions were reviewed through the owner's senior-frontend skill during this discussion. All decisions were kept (K1 to K9), and the owner accepted every refinement (R1 to R9) and both ideas (I-A, I-B) in `06.1-FE-REVIEW.md`. They are folded into the decisions below.

### The finish model
- **D-01: The finish is two choices, a design and a wood, and every combination is allowed.**
  - **Designs (7):**
    - **Classic:** moulded top, arched plinth on feet. This is today's build.
    - **Modern:** slab top, straight recessed base, no moulding. It was "walnut done properly".
    - **Display:** thick slab top, dark recessed base so the cabinet seems to float.
    - **On legs:** apron with splayed, tapered legs.
    - **Library:** crown with cap, cove and dentils, moulded plinth, a thin brass line along every shelf front.
    - **Plywood:** striped ply layers on every front edge, slightly rounded corners, low recessed base.
    - **Plywood on legs:** ply edges and rounded corners on two splayed legs. This is the old "modern birch plywood".
  - **Woods (5):** warm brown (today's), walnut, oak, birch, mahogany.
  - The seven looks the owner liked earlier are combinations:

    | Earlier look | Combination |
    |---|---|
    | Classic | Classic + warm brown |
    | Walnut done properly | Modern + warm brown |
    | Walnut display | Display + walnut |
    | Oak on legs | On legs + oak |
    | Library | Library + mahogany |
    | Modern birch plywood | Plywood on legs + birch |
    | Plywood with painted backs | Plywood + birch + painted backs |

  - Odd pairs (Library in birch, for example) are allowed and shown in the mock-up round.
  - — **Reversibility:** costly — going back to fixed finishes means migrating the stored setting and rebuilding the settings tiles and the CSS layering.
- **D-02: The wood brings the wall.**
  - Each wood defines the wall colour, the floor and skirting tones, the wall text colour and whether the wall is light or dark (which picks the logo).
  - Starting walls come from the earlier mock-ups: warm brown on today's dark brown, oak on slate blue, mahogany on bottle green, birch on light plaster. Walnut's wall is set in the mock-up round.
- **D-03: Painted backs is an extra on/off option that works with any design.**
  - The cubby backs are painted a dark colour (the earlier mock-up used petrol) instead of showing the wood back.
- **D-04: Three independent CSS layers (R1).**
  - The page root carries five plain attributes: design, wood, depth, lights and backs.
  - The **design** layer owns every size: top, base, legs, side trim, overhang, and the space each section reserves in its aspect ratio.
  - The **wood** layer owns only colours: grain, wall, floor, skirting, chrome and the logo tone.
  - The **modifiers** (depth, lights, painted backs, evening) only add overlays.
  - Changing wood, lights, depth or backs therefore can never shift the layout or clip a leg.
  - The same attributes work on the settings preview's wrapper (D-20), so the preview runs the real cabinet code.
  - This supersedes the single `finish-*` body class from the Phase 6 slot.
- **D-05: Today's look is frozen and proven (K3).**
  - Classic + warm brown + no painted backs + Shaded + lights Off must render pixel-identical to the current release.
  - A before/after screenshot check at desktop and phone width proves it. Only new options may add to it.
  - The planned layout-engine balancing (D-34) changes section contents. So compare classic before and after the CSS split on the **same** layout version, then balance as a separate step.
- **D-06: The stored setting grows, and older data still restores (R2).**
  - The owner-data `finish` value becomes design, wood, painted backs, lights and depth.
  - A file or export from before this phase (`finish: "classic"`) restores as today's look.
  - Unknown values fall back per field, not all at once.
  - The allow-lists replace `Finishes.Allowed`. Every value is checked server-side before use (it ends up in markup).
  - — **Reversibility:** one-way — the owner-data schema version goes up. The previous release cannot read a file saved by this one, so a rollback after the owner publishes a new look falls back to an earlier owner-data copy or the default look. Plan the schema bump and rollback behaviour explicitly.

### Depth
- **D-07: Depth is its own setting, the same on every design (K4).**
  - **Flat:** no shading.
  - **Shaded:** today's shadow under each shelf. This is the default.
  - **Deep:** inner walls and floor drawn in perspective, plus a thin lit top face on each shelf. Display's earlier "seen slightly from above" view lives here, not in the Display design.
  - No design carries depth of its own.
  - The planked back (Classic) and the plain ply sheet (Plywood) belong to the design's back construction, not to depth.

### Lights
- **D-08: One three-way control: Off · Always on · Evenings only.**
  - "Evenings only" is the follow-day-and-night behaviour.
  - This replaces the two switches of the Phase 6 context (D-33).
- **D-09: Evenings follow the season (R7).**
  - Lights come on about 30 minutes before sunset and go off at sunrise.
  - Times come from a fixed date table at one latitude: local clock times with summer time already applied, a few points per month, interpolated.
  - The visitor's own clock is used; no location data at all.
  - A page left open across either moment fades the same way.
- **D-10: The lights fade on after the first paint (Phase 6 context, D-34).**
  - The fade takes about 2 s. Reduced motion switches instantly.
- **D-11: One light layer per section, faded on the compositor (R5).**
  - Each section gets one extra decorative element, hidden from assistive technology, next to top, trim and base. It holds the light for all its cubbies.
  - Only its opacity animates. No per-cubby gradient animation.
- **D-12: Box fronts get almost no light (R4).**
  - The light is strongest on the back panel and box tops, and only slightly lifts box fronts.
- **D-13: Whether the room dims in the evening is decided by sight in the mock-up round.**
  - The choice is between the wall and the cabinet's outside darkening a little in Evenings mode after dusk, and lights only.
- **D-14: If the room dims, "evening" is marked before the first paint (R6).**
  - A tiny external script in the page head reads the clock and marks evening. It is a file, not inline code, under the strict CSP.
  - The room is dark from the first frame, and the lights still fade on.

### Walls and what follows
- **D-15: The wall is a room (K6).**
  - It has a wall colour with a soft light falloff from above, plus a floor and a skirting board in tones that suit the wood.
- **D-16: The floor is decided by sight in the mock-up round.**
  - Option one: a floor patch with skirting per section, fading at the sides.
  - Option two: one continuous floor per row of sections.
  - **Cost to weigh (R8):** sections clip their painting at their own edges (paint containment for cheap scrolling). A floor through the gaps therefore needs either a page-level floor that knows where rows break (script on every resize) or giving up that clipping. The patch per piece fits the current structure for free.
- **D-17: In the evening the lights reach the floor (I-B).**
  - A faint warm glow on the floor and skirting just in front of each lit cabinet.
- **D-18: The official dark "Powered by BGG" logo on light walls.**
  - **Source:** the standard RGB SVG `Color/SVG/powered-by-bgg-rgb.svg` from the same official logo pack the white logo came from. The owner has the pack locally, and its reversed SVG matches the hash pinned in `Cabinet.Service/wwwroot/img/NOTICE.md`.
  - The standard SVG has SHA-256 `527357eff019297fa1a1e81002723c1eb5bbbf8ae80e5a31fdae17bf8f82d8cc`, dark navy text (`#3F3A60`), the same orange mark and the same 342 × 76 view box. It swaps in without any layout change.
  - Copy it unchanged beside the white one, add it to `NOTICE.md`, and pin its hash in the unit test like the existing logo.
  - The page shows the dark logo on light walls and the white one on dark walls. The logo itself is never modified (BGG terms).
- **D-19: Only the public page's chrome follows the wall.**
  - The header, status line, footer, buttons and focus rings on the public cabinet take the wall's colours. That includes the cabinet shown at the owner address.
  - The game card (paper look) is the same everywhere.
  - The owner pages (pictures, locations, settings) keep today's look whatever the finish.

### Settings page and switching
- **D-20: Preview first, then "Use for everyone".**
  - The settings page shows a real cabinet section that changes as the owner taps designs, woods and options.
  - Nothing changes for visitors until **Use for everyone**. **Back to current** drops the trial.
  - This replaces the tap-saves-at-once behaviour of the Phase 6 finish slot.
- **D-21: Choose by sight with tiles that preview themselves (Phase 6 context D-36, I-A).**
  - Design tiles are drawn in the chosen wood, and wood tiles on the chosen design, each as a small cropped cubby corner.
  - Under them sit the painted-backs switch, the lights control and the depth control.
- **D-22: A Day · Evening toggle on the preview.**
  - It shows the evening look (lights, and the dimmed room if chosen) at any hour. It affects only the owner's preview.
- **D-23: Open pages change live.**
  - After "Use for everyone", open pages switch within a few seconds through the existing live updates, with a short cross-fade (instant under reduced motion). An open game card stays open.
- **D-24: A design change keeps the visitor's place (R9).**
  - Designs reserve different heights, so the switch uses the browser's view transition where available. The section in view stays where it was.
  - Changing wood, lights, depth or backs moves nothing (D-04).
- **D-25: The default is today's look.**
  - Classic, warm brown, no painted backs, lights Off, Shaded.
  - The release changes nothing visible until the owner publishes a new look.

### Contrast and checks
- **D-26: Spine contrast is a unit test over what can fall on a box (R3).**
  - Every palette colour is tested against every light state × depth (nine cases) and must stay at or above 4.5:1. Wood and design never touch a box face.
- **D-27: Chrome contrast is a unit test per wall.**
  - Header, status line and footer text, and the logo choice, are checked on each of the five walls in day and evening.
  - Focus rings must reach at least 3:1 on every wall and every wood frame.
  - This follows the existing `CardContrastTests` and `OwnerContrastTests`.
- **D-28: The cabinet stays smooth on a phone.**
  - Textures stay on the few large elements. The light fade is opacity only (D-11).

### Mock-up round
- **D-29: The round starts from the recovered earlier mock-ups.**
  - They are in `ui-refs/earlier-mockups/` (screenshots plus replayed sources), ported onto today's cabinet with synthetic content.
- **D-30: A switcher page plus screenshot sheets.**
  - One static page of the real cabinet with plain buttons for design, wood, painted backs, lights (including evening) and depth. The owner tries combinations in the browser pane.
  - Full desktop and phone sheets with crops (corner, shelf edge, base, legs) for the seven earlier looks (D-01 table).
  - One overview grid of all 35 design × wood pairs as small cubby corners.
- **D-31: Everything in one round.**
  - A second round covers only the looks the owner wants adjusted.
- **D-32: Decided by sight in the round, per design:**
  - on a phone, every section a full piece of furniture (today) or the sections joined into one tall piece (top only on the first, base and legs only on the last);
  - room dimming (D-13);
  - floor (D-16).

  If "joined" is picked for Classic, that is an explicit exception to D-05, approved by the owner in the round.
- **D-33: Persist right away.**
  - Approved mock-up sources and key screenshots go into the phase directory as soon as the owner picks: synthetic content only, absolute paths scrubbed.

### Established Patterns
- **Strict CSP** (`default-src 'self'`): no inline styles or scripts. Values reach CSS through attributes, classes or `style.setProperty`. The head script (D-14) is an external file.
- **Server-rendered first paint:** the look is written into the markup by the server, so there is no flash. Only evening depends on the client clock.
- **Paint containment:** sections use `content-visibility: auto`, so everything a design draws (legs, crowns, floor, shadows) must end inside the section box (D-16).
- **Versioned owner data** through the atomic JSON stores (`AtomicJsonFile`, `StoredJson`, `StrictEnumConverter`), with earlier versions kept (D-06).
- **Tests:**
  - unit tests on xunit.v3 and FluentAssertions;
  - `node --test` for page scripts and CSS (`build/tests/cabinet-css.test.mjs`, `owner-finish.test.mjs`);
  - Playwright browser tests (`Cabinet.BrowserTests/OwnerFinishTests.cs`, `ReducedMotionTests.cs`, `CabinetPolishTests.cs`);
  - `FakeTimeProvider` for time rules.
- **Comments:** `///` doc comments only in C#, `/** */` only in JS. No planning references outside `.planning/`.

### Integration Points
- `_Layout.cshtml`: the root attributes for design, wood, depth, lights and backs on both ports, and the head script for evening.
- `render.js` and `cabinet.css`: the light layer, and the design, wood and modifier layers.
- `Settings.cshtml(.cs)` and `owner-finish.js`: preview, tiles, controls, Use for everyone, Back to current, Day · Evening.
- The live hub: a look-change broadcast, and the client applying it with a view transition.
- `_Footer.cshtml`: the logo variant chosen by wall tone.
- The layout engine and golden files: balanced sections.
- `OwnerLinkFetcher`, `OwnerLinkWorker` and `Pictures.cshtml.cs`: the separate slot for the interactive check.

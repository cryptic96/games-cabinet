# Phase 06.1: Code Review Report

**Reviewed:** 2026-10-15
**Depth:** standard
**Files Reviewed:** 47
**Status:** issues_found

## Summary

Production code and CI only; the test projects were out of scope. The phase replaces the single stored finish with a five-field look, adds the
schema upgrade, the live look switch, the evening lamp, a separate fetch slot for the owner's link check, and balanced section layout.

What holds up under review:

- **Markup injection.** Every look value that reaches markup (`data-design`, `data-wood`, `data-backs`, `data-lights`, `data-depth`) is normalised
  against an allow-list on the server first (`SiteLook.Current`, `LookStatus.From`, `Settings.Populate`). The client writes pushed values with
  `setAttribute`, never as HTML. Owner-side text uses `textContent`.
- **CSP.** No inline script, inline style or event attribute was added. The only style writes are CSSOM `setProperty` calls, which the policy allows.
- **Public status.** `LookStatus` carries only the five allow-listed values and one boolean. No owner data, location or picture reaches it.
- **Owner routes.** The look handlers sit on the owner-only Razor Page, so antiforgery is automatic. Redirect codes come from a fixed set.
- **Picture client.** The owner-check client keeps the credential-free transport and adds no authorization handler.
- **Planning references, `//` comments, personal data.** None found in any reviewed source file.

No blockers. The real problems are in the owner-data schema upgrade and in the live look switch. The upgrade has a weakened corruption guard and a
rollback copy that is not guaranteed. The look switch has an ordering race.

## Warnings

### WR-01: A stored file with `schemaVersion` of 0 or below is no longer rejected; the upgrade stamps it as version 2

**File:** `Cabinet.Repository/Storage/OwnerDataStore.cs:174-193` and `:205-239`
**Issue:** `Parse` calls `UpgradeToCurrent(content, known.SchemaVersion)` with no lower bound. `UpgradeToCurrent` upgrades every version below 2 and
unconditionally writes `root["schemaVersion"] = 2`. The later guard `data.SchemaVersion < 1` (line 192) therefore can never fire. A file whose
header says `0` or `-5` used to be reported as unreadable and left untouched. Now it loads as ready data. The first save then replaces it, with only
the forced copy as a safety net. `OwnerDataExport.Check` still guards `header.SchemaVersion < 1`, so the two readers disagree.
**Fix:** Refuse below the first format before upgrading:
```csharp
if (known.SchemaVersion < 1)
{
    return Unreadable("malformed");
}

var upgraded = UpgradeToCurrent(content, known.SchemaVersion);
```
Also drop the now-dead `data.SchemaVersion < 1` check, or keep it as a post-condition on the upgraded bytes.

### WR-02: The forced rollback copy can fail silently and the save then overwrites the old-format file anyway

**File:** `Cabinet.Service/Owner/OwnerDataService.cs:459-475` (callers at `:264`, `:313`, `:363`, `:515`)
**Issue:** The new rule says a file in an older format is always copied because "after the save no earlier release can read the file, and the copy is
the only one it can". But `KeepEarlierVersionWhenDue` catches `IOException` and `UnauthorizedAccessException` itself, logs a warning and returns.
Every call site then goes on to `_store.Save`, and each site's own `catch` never sees the failure. If the copy fails (disk full, a permission problem
on the versions directory), the one-time upgrade proceeds. The old-format file is replaced by a file no earlier release can read, with no copy
anywhere. This is the one write where the copy is the whole point.
**Fix:** For the old-format case only, let the failure refuse the save. Split the helper so the forced copy is not swallowed:
```csharp
private void KeepEarlierVersionWhenDue(DateTimeOffset now)
{
    var older = _store.StoredSchemaVersion() < OwnerData.CurrentSchemaVersion;

    try
    {
        if (older || _store.NewestEarlierVersionAt() is not { } newest || now - newest > VersionInterval)
        {
            _store.KeepEarlierVersion(now);
        }
    }
    catch (Exception exception) when (exception is IOException or UnauthorizedAccessException)
    {
        _logger.LogWarning("An earlier version of the owner data could not be kept: {ExceptionType}", exception.GetType().Name);

        if (older)
        {
            throw;
        }
    }
}
```
The callers' existing `catch` blocks then turn it into a refused save.

### WR-03: The rollback copy can be overwritten or pruned, so the guarantee is not durable

**File:** `Cabinet.Repository/Storage/OwnerDataStore.cs:93-107` and `:134-135`
**Issue:** Two ways the format-1 copy disappears:
1. The version file name has one-second resolution (`yyyyMMdd'T'HHmmss'Z'`) and `KeepEarlierVersion` writes with an atomic replace. A second
   copy taken within the same second overwrites the first. The upgrade save is followed by an unconditional copy in a restore flow, so a restore
   right after the upgrade save can replace the format-1 copy with a format-2 one.
2. Retention is the 10 newest copies by timestamp. After ten more hourly copies the only format-1 copy is pruned. Nothing marks it as the rollback
   copy, and the documented purpose ("so the release that wrote it can be rolled back to") quietly stops being true.

**Fix:** Keep the pre-upgrade copy under a name that is exempt from the count, for example `owner-data.pre-v2.json`. Write it only when it does not
already exist, and never prune it. At minimum, make `KeepEarlierVersion` refuse to overwrite an existing file name.

### WR-04: Restoring a format-1 backup silently resets the look every visitor sees

**File:** `Cabinet.Repository/Storage/OwnerDataStore.cs:222-231`, reached from `Cabinet.Repository/Storage/OwnerDataExport.cs:147`
**Issue:** `UpgradeToCurrent` replaces the look with `CabinetLook.Default` for any older file. That is correct for reading the stored file. For a
restore it means that when the owner restores an old backup, whether a downloaded file or an earlier version, the look they chose since is
overwritten with classic/brown for all visitors. The restore preview figures (locations, placed games, picture choices) do not mention it, and the
change log only says "restored". The owner never decided to change the look.
**Fix:** For a restore whose source format has no look, carry the look already on the server into the restored data. Do it in `RestoreAsync` when
the candidate's `FormatVersion < 2`, or have the preview say that the look will be reset.

### WR-05: Overlapping look applications on an open page can leave an older look on screen

**File:** `Cabinet.Service/wwwroot/js/look-switch.js:277-298` (`showLook`) and `:239-262` (`crossFade`)
**Issue:** `showLook` compares the incoming look with the root's attributes once, at the top, and then writes later. Two gaps follow:
- Look A turns the lights on while the evening script is not loaded, so `await loadEveningScript(doc)` takes a network round trip. Look B (newer)
  arrives in that gap. It is not stale, finds the attributes unchanged, and applies. A resumes and writes its own values over B.
- With a cross-fade, the attributes only change inside the view-transition update callback. A newer look that reverts to what the page shows now
  finds `changed` empty, applies nothing, and the pending callback then writes the older look.

`isStale` only orders by the status clock; it does not serialise the writes. The page ends up showing a look that is not the latest one, until the
next push or status refresh. No later event corrects it if B was the final state.
**Fix:** Keep one "latest wanted look" per root and make the write read it at execution time instead of a closure over the old look:
```js
const wanted = new WeakMap();

async function showLook(root, look) {
  wanted.set(root, look);
  // ...after any await and inside the update callback:
  const current = wanted.get(root);
  writeLook(root, current);
}
```
Compare `changed` against the latest wanted look, not the root's attributes, when a transition is pending.

### WR-06: `LiveConnectionLimiter.IsAdmitted` has no production caller; and `TryAdmit` rejects an already admitted id at the cap

**File:** `Cabinet.Service/Live/LiveConnectionLimiter.cs:42-49` and `:23-39`
**Issue:** `IsAdmitted` was added in this phase but nothing outside the tests calls it. It is a public API with nothing to guard. Separately, `TryAdmit`
increments before checking for a duplicate id. At the cap, a repeat call for a connection that already holds a place sees `count + 1 > max`,
returns `false` and decrements, although the connection is admitted. A caller that closes on `false` would drop a legitimate connection. The
increment-then-check pattern also makes concurrent callers briefly see a count above the real one, so one can be rejected while room exists.
**Fix:** Remove `IsAdmitted` until a caller needs it, or use it on the repeat path. Add the id first, then count, and roll the entry back on overflow:
```csharp
if (!_admitted.TryAdd(connectionId, 0)) { return true; }
if (Interlocked.Increment(ref _count) > options.MaxConnections)
{
    Interlocked.Decrement(ref _count);
    _admitted.TryRemove(connectionId, out _);
    return false;
}
return true;
```

## Info

### IN-01: Look names and the light-wall rule are duplicated across C#, JS and CSS

**File:** `Cabinet.Domain/Owner/CabinetLook.cs:62-91` and `:55`; `Cabinet.Service/wwwroot/js/owner-format.js:123-137`; `Cabinet.Service/wwwroot/css/cabinet-wood.css:105,188`
**Issue:** The display names exist twice (C# `DesignName`/`WoodName`/`LightsName`/`DepthName` and JS `LOOK_NAMES`). The "light wall" fact exists three
times: `CabinetLook.HasLightWall` (walnut, birch), the `--room` values in CSS, and the `data-logo-*` swap. They agree today, but nothing ties them
together. A new wood added in one place and not the others fails quietly (wrong logo, wrong name).
**Fix:** Have the server render the names into the page, as `data-*` or the `LookStatus`, and read them in JS. Add one test that every allow-listed wood has a CSS block and a known wall tone.

### IN-02: Ids and constants still say "finish" after the rename to look

**File:** `Cabinet.Service/Pages/Owner/Settings.cshtml:20-21,127`; `Cabinet.Service/Pages/Owner/Settings.cshtml.cs:45`; `Cabinet.Service/wwwroot/js/owner-look.js:171`
**Issue:** `id="finish"`, `finish-heading`, `finish-status` and `LookAnchor = "finish"` keep the old name. A future reader searching for "look" misses the anchor and the status region.
**Fix:** Rename to `look`, `look-heading`, `look-status` in the page, the model constant and `findParts`. Keep a redirect-safe anchor if old bookmarks matter.

### IN-03: Copy that is relative to a moment in time

**File:** `Cabinet.Service/Owner/OwnerStrings.cs:~575,~600-603`
**Issue:** "Shaded is today's look" and "Today's wood and wall." describe the default as of this release. Both go stale once the default changes, and they are shown to the owner for good.
**Fix:** Say "the default" and name what it is ("Shaded is the default.", "The default wood and wall.").

### IN-04: The evening table is a single mid-European reference, but the hint promises the visitor's own sunset

**File:** `Cabinet.Service/wwwroot/js/evening.js:1-9,24-70`; `Cabinet.Service/Owner/OwnerStrings.cs:~571`
**Issue:** The lamp-on and sunrise minutes come from one fixed 52 degrees north table, shifted by the visitor's summer-time flag. For a visitor in the southern hemisphere, or far from that latitude, "Evenings only follows sunset and sunrise by each visitor's own clock" is not accurate. The code comment says so; the owner-facing hint does not.
**Fix:** Reword the hint ("follows an approximate European sunset and sunrise on each visitor's own clock") or document the limit next to the setting.

### IN-05: Control-flow by exception and a nested `Parse` upgrade path add complexity without a comment

**File:** `Cabinet.Domain/Layout/CabinetLayoutEngine.cs:157-168` and `Cabinet.Repository/Storage/OwnerDataStore.cs:205-239`
**Issue:** `TryPlaceAll` treats `InvalidOperationException` from the placer as "this budget does not fit". The same exception type also signals real placer defects, which a balance attempt would hide and leave on the plain arrangement. `TryBalance` is also a double loop that re-places every game for each of `rows x sections` candidates. This is a performance matter and outside the review scope, but the exception filter is a correctness smell.
**Fix:** Return a result from the placer (a `TryPlace...` that reports "no room") instead of catching a general exception type, or throw a dedicated `NoRoomException` and catch only that.

### IN-06: One commit hash pinned in the secrets-scan allow-list is fragile

**File:** `.gitleaks.toml:129-136`
**Issue:** The allow-list entry is tied to a single commit id. A rebase, squash merge or history rewrite changes the id and the full-history scan fails again on the same text, as it did before this entry was added. The match is otherwise tightly scoped (`^name\.local\s$`), which is good.
**Fix:** Pin by fingerprint (`commit:file:rule:line`) as the repository's own note recommends, or keep the entry and add a one-line reminder in the lint step that a history rewrite needs the id updated.

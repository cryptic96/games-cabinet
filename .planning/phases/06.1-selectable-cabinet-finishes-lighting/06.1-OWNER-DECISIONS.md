## P1. Balanced desktop sections vs. "adding a game moves only one cubby"

**The conflict.** D-34 says the engine spreads games so all desktop sections come out about the same height. Today's layout promises the opposite: adding a game changes only the cubby it lands in, and existing sections are never redesigned to make room. The tests enforce that promise over 200 seeds. Spreading games evenly means that adding one game can move other games between sections. So the promise has to change on purpose, with its tests and docs, before any code is written.

The phone layout stays exactly as it is in every option.

| Label | What it means | Cost |
|---|---|---|
| **P1-A (rec)** | **Prototype first, decide by sight.** Build the even spread on the 65- and 400-game samples. You get before/after desktop sheets plus a count of how many games move when one game is added. Then you choose the new promise, for example "games keep their reading order, but adding a game may shift games between desktop sections". It is a blocking checkpoint early in the phase, running in parallel with the mock-up round. | One extra review step. No wasted engine work if you don't like the moves. |
| P1-B | **Full spread, accept the moves now.** Every desktop section gets about the same number of used rows. Adding a game can shift games across all desktop sections. Reading order is kept. | The desktop stability tests are replaced by an order-kept test. |
| P1-C | **Balance only the last two sections.** Every full section stays as it is today. The last two sections share their games evenly, so only those can move. | The earlier full sections stay taller than the last two, so the sections are not all the same height. Only a partial answer to D-34. |
| P1-D | **Draw instead of move.** Nothing moves. The last section is drawn at full height, with empty shelves. | Brings back the tall stretch of empty shelves that the trimming rule was made to avoid. Doesn't really meet D-34. |

## P2. Reference point for the sunset table

The UI spec fixes the table at 52° N but leaves out the longitude. Longitude shifts local sunset by 4 minutes per degree. The table also needs to follow each year's real summer-time change dates. Baking fixed dates into the table is up to 49 minutes wrong. The fix is a standard-time table plus the visitor's own summer-time flag, which brings the worst error under 1 minute.

| Label | What it means |
|---|---|
| **P2-A (rec)** | **52° N, 5° E,** with the visitor's own summer-time flag. Accurate for the Netherlands and nearby. In the docs it is described only as "a mid-European reference point", with no place name. It is country-level and says nothing more than the site's language does. |
| P2-B | **52° N, with the longitude taken from the visitor's time zone** (offset × 15°). Generic, with no fixed place in the repository at all. For Dutch visitors the lamp comes on about 40 minutes early (about 70 minutes before sunset instead of 30). |

## P3. What a rollback costs after the owner-data format change

Locked decision: the owner-data schema version goes up. The previous release cannot read a file saved by the new one. Research found a sharper edge: the new release rewrites the file on **any** owner save (moving a location, choosing a picture), not only on a look change. The automatic "earlier versions" copy is taken at most once an hour, so the old-format file might not be kept.

| Label | What it means |
|---|---|
| **P3-A (rec)** | **Keep the schema bump, and force a copy of the old-format file before the first new-format save**, whatever the hourly timer says. A rollback then lands on that copy through the existing recovery panel. Tested. |
| P3-B | **Don't bump the schema.** Stay at version 1, add an optional `look` object, and keep writing the old `finish` field too. A rollback loses nothing. This overrides the locked decision, and the old field stays around for good. |

## P4. Safari engine (WebKit) in the browser tests

The UI spec wants the "live switch keeps your place" test to run in Chromium and WebKit. WebKit isn't installed locally or in CI.

| Label | What it means | Cost |
|---|---|---|
| **P4-A (rec)** | **One extra CI step installs WebKit, and one test launches it explicitly.** The scroll-keeping logic is also covered by fast Node tests. If WebKit won't install on the CI runner, fall back to P4-B and note it in the summary. | About 1–2 minutes and one browser download per CI run. |
| P4-B | **Node logic tests only, plus a manual Safari check** on the deployed site during acceptance. | No CI cost, but there's no automated Safari proof. |

## P6. "Check link" gets its own fetch slot

D-35: the owner's check must never wait behind the background link worker.

| Label | What it means |
|---|---|
| **P6-A (rec)** | **A second, separate fetch slot for the owner's check.** At most two requests to the image host can then overlap: one background and one owner-initiated, both rare. Each slot keeps its own politeness gap. |
| P6-B | **The owner's check pre-empts the background worker.** The worker's request in flight is cancelled and retried later. There is never more than one request to the image host at a time, but the change is more involved. |

# Balanced desktop sections: before, after, what it costs, and which promise to keep

Review document for the owner. Answer by label (B1, B2 or B3) plus "setting yes" or "setting no" at the bottom.

All pictures use the invented sample collections (65 and 400 games), drawn at the committed look (33 percent of boxes face out). They were taken with a DejaVu-based font setup so they match what the CI machine draws. Nothing here is turned on yet: the balancing exists in the engine behind a server setting that is off, and every recorded layout is unchanged.

## What changes, in plain words

Today the desktop cabinet fills one section completely, then the next, and the last section is drawn only as tall as the games in it. With 65 games that gives one full section and one short one (two shelf rows); with 400 games, seven full sections and a last one three rows tall. A short last section looks unfinished next to full ones.

With the balancing on, the same games, in the same order, are placed again with a limit on how many shelf rows each section may use. The engine takes the smallest limit that still needs no more sections than before, so the games spread over the same number of sections and every desktop section is drawn within one shelf row of every other. No section is left short at the end. The phone cabinet never balances (it is one column, and a short last section there just reads as the end of the shelf).

| Sample | Setting off: shelf rows per section | Setting on: shelf rows per section |
|---|---|---|
| 65 games | 5, 2 | 4, 4 |
| 400 games | 5, 5, 5, 5, 5, 5, 5, 3 | 5, 5, 5, 5, 5, 5, 4, 4 |

The balancing changes more for small collections (65 games: a lopsided pair becomes an even pair) than for large ones (400 games: only the last three rows become two sections of four). Each section is always whole rows, so "within one row" is the finest evenness the furniture allows.

## How many games move when one game is added

The layout has no memory, so adding a game re-lays the cabinet. The numbers below add one invented game to a collection and compare the layout before and after: how many games end up in a different section, and how many cubbies (shelf compartments) change at all. "Setting off" is today's behaviour. The cases are the same 200 seeds the stability tests use (collections of 120 games, 15 percent expansions, one invented game appended), and for each of the 65 and 400 samples 50 different invented games, one at a time.

Committed look (33 percent face-out):

| Collection | Setting | Cases where any game changes section | Games changing section: median / largest | Cubbies changed: median / largest |
|---|---|---|---|---|
| 120 games, 200 seeds | off | 0 percent | 0 / 0 | 1 / 11 |
| 120 games, 200 seeds | on | 10 percent | 0 / 41 | 1 / 34 |
| 65 sample, 50 games | off | 0 percent | 0 / 0 | 1 / 1 |
| 65 sample, 50 games | on | 0 percent | 0 / 0 | 1 / 1 |
| 400 sample, 50 games | off | 6 percent | 0 / 31 | 1 / 56 |
| 400 sample, 50 games | on | 6 percent | 0 / 36 | 1 / 57 |

At the default 25 percent face-out the picture is the same (120 games: 6 percent of cases move games with the setting on, largest 37; 400 sample: identical to off, because there the last section is already four rows).

How to read this:

- Most of the time (90 to 100 percent of added games) nothing changes section at all, with the setting on or off, and the typical added game still changes exactly one cubby.
- The cases where games move with the setting off are a new game that joins an existing series: the whole series is placed together, so it moves. That is today's accepted exception and it is the whole 6 percent in the 400 sample.
- With the setting on there is one more cause: the added game changes how tightly the games must be packed, so the row limit changes and a run of games shifts across a section boundary. In the 120-game collections that happens in about one case in ten; when it happens the largest shift is about 40 games, the median is zero.
- Cost of the calculation: a 400-game desktop layout takes about 0.9 s with the setting on versus 0.08 s off (release build, a single core). It runs once per collection version and is then cached, and the phone layout is not affected.

## What the layout promise says today, and what would replace it

Today: adding a game changes at most the cubby it lands in (and the neighbouring cubby for an expansion's column), except when it joins a series. That is checked by the stability tests and written in the layout documentation under "Stability".

Reading order, for the record: games are still taken in collection order and each goes into the first place that fits, as today. Because that is first-fit, the order you read the cabinet in is not exactly collection order even today, and with balancing on it is not identical to today's either (the row limit changes where the first fit is). Every game still appears exactly once and every series still runs on without leaving a cubby out. If you want the exact same cubby-by-cubby sequence as today, balancing is not possible with fixed rows; that is why this is a choice and not a bug.

### B1 Full spread (recommended)

Proposed wording: "Games keep their reading order. Adding a game changes at most one cubby inside a section, but it may move games across desktop section boundaries so the sections stay within one shelf row of each other. The phone cabinet keeps today's promise: adding a game changes only the cubby it lands in."

- Every desktop section about the same height; no short last section anywhere.
- Cost: the occasional shift across section boundaries described above (about one added game in ten for a collection of 120 games; none in about nine of ten).

### B2 Balance only the last two sections

Proposed wording: "Only the last two desktop sections can change when a game is added; every earlier section keeps its games."

- Earlier sections never move.
- On the two samples it looks the same as B1: in the 65 sample the last two sections are the whole cabinet (4 and 4), and in the 400 sample the last two are the five-row and three-row sections, which become 4 and 4. The sheets above therefore show B2 as well. The two differ on collections where the full spread would also trim earlier sections (for example when the last section is far shorter than the rest), where B2 leaves the earlier ones five rows tall.
- It needs a small change to the search (a row limit for the last two sections only) before it could be measured on its own; the move counts above are for B1, and B2 would be lower (only the last two sections can move) but not measured yet.

### B3 Your own wording

Write the promise you want. It may need another measurement before building if it is not one of the two above.

### The setting

Independent of the choice above: should the balancing stay a documented server setting `Layout:BalanceSections` (on by default, off gives today's arrangement, the same way `Layout:GroupSeries` works)? Recommended: yes. It costs one more line in the settings table and lets the owner switch back without a release.

## Technical notes (for the record)

- The balancing is production code behind `Layout:BalanceSections` (off by default) and a design flag that only the desktop design sets. With the setting off, the fingerprint, the layout version (15) and every recorded layout are unchanged.
- Measured with a throwaway harness kept outside the repository; none of it is committed.

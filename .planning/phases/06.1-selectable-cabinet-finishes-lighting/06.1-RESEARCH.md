### The finish model
- **D-01: The finish is two choices, a design and a wood, and every combination is allowed.**
  - **Designs (7):**
    - **Classic:** moulded top, arched plinth on feet. This is today's build.
    - **Modern:** slab top, straight recessed base, no moulding. It was "walnut done properly".
    - **Display:** thick slab top, dark recessed base so the cabinet seems to float.
    - **On legs:** apron with splayed, tapered legs.
    - **Library:** crown with cap, cove and dentils, moulded plinth, a thin brass line along every shelf front.
    - **Plywood:** striped ply layers on every front edge, slightly rounded corners, low recessed base.
    - **Plywood on legs:** ply edges and rounded corners on two splayed legs. This is the old "modern birch plywood".
  - **Woods (5):** warm brown (today's), walnut, oak, birch, mahogany.
  - The seven looks the owner liked earlier are combinations:

    | Earlier look | Combination |
    |---|---|
    | Classic | Classic + warm brown |
    | Walnut done properly | Modern + warm brown |
    | Walnut display | Display + walnut |
    | Oak on legs | On legs + oak |
    | Library | Library + mahogany |
    | Modern birch plywood | Plywood on legs + birch |
    | Plywood with painted backs | Plywood + birch + painted backs |

  - Odd pairs (Library in birch, for example) are allowed and shown in the mock-up round.
  - — **Reversibility:** costly — going back to fixed finishes means migrating the stored setting and rebuilding the settings tiles and the CSS layering.
- **D-02: The wood brings the wall.**
  - Each wood defines the wall colour, the floor and skirting tones, the wall text colour and whether the wall is light or dark (which picks the logo).
  - Starting walls come from the earlier mock-ups: warm brown on today's dark brown, oak on slate blue, mahogany on bottle green, birch on light plaster. Walnut's wall is set in the mock-up round.
- **D-03: Painted backs is an extra on/off option that works with any design.**
  - The cubby backs are painted a dark colour (the earlier mock-up used petrol) instead of showing the wood back.
- **D-04: Three independent CSS layers (R1).**
  - The page root carries five plain attributes: design, wood, depth, lights and backs.
  - The **design** layer owns every size: top, base, legs, side trim, overhang, and the space each section reserves in its aspect ratio.
  - The **wood** layer owns only colours: grain, wall, floor, skirting, chrome and the logo tone.
  - The **modifiers** (depth, lights, painted backs, evening) only add overlays.
  - Changing wood, lights, depth or backs therefore can never shift the layout or clip a leg.
  - The same attributes work on the settings preview's wrapper (D-20), so the preview runs the real cabinet code.
  - This supersedes the single `finish-*` body class from the Phase 6 slot.
- **D-05: Today's look is frozen and proven (K3).**
  - Classic + warm brown + no painted backs + Shaded + lights Off must render pixel-identical to the current release.
  - A before/after screenshot check at desktop and phone width proves it. Only new options may add to it.
  - The planned layout-engine balancing (D-34) changes section contents. So compare classic before and after the CSS split on the **same** layout version, then balance as a separate step.
- **D-06: The stored setting grows, and older data still restores (R2).**
  - The owner-data `finish` value becomes design, wood, painted backs, lights and depth.
  - A file or export from before this phase (`finish: "classic"`) restores as today's look.
  - Unknown values fall back per field, not all at once.
  - The allow-lists replace `Finishes.Allowed`. Every value is checked server-side before use (it ends up in markup).
  - — **Reversibility:** one-way — the owner-data schema version goes up. The previous release cannot read a file saved by this one, so a rollback after the owner publishes a new look falls back to an earlier owner-data copy or the default look. Plan the schema bump and rollback behaviour explicitly.

### Depth
- **D-07: Depth is its own setting, the same on every design (K4).**
  - **Flat:** no shading.
  - **Shaded:** today's shadow under each shelf. This is the default.
  - **Deep:** inner walls and floor drawn in perspective, plus a thin lit top face on each shelf. Display's earlier "seen slightly from above" view lives here, not in the Display design.
  - No design carries depth of its own.
  - The planked back (Classic) and the plain ply sheet (Plywood) belong to the design's back construction, not to depth.

### Lights
- **D-08: One three-way control: Off · Always on · Evenings only.**
  - "Evenings only" is the follow-day-and-night behaviour.
  - This replaces the two switches of the Phase 6 context (D-33).
- **D-09: Evenings follow the season (R7).**
  - Lights come on about 30 minutes before sunset and go off at sunrise.
  - Times come from a fixed date table at one latitude: local clock times with summer time already applied, a few points per month, interpolated.
  - The visitor's own clock is used; no location data at all.
  - A page left open across either moment fades the same way.
- **D-10: The lights fade on after the first paint (Phase 6 context, D-34).**
  - The fade takes about 2 s. Reduced motion switches instantly.
- **D-11: One light layer per section, faded on the compositor (R5).**
  - Each section gets one extra decorative element, hidden from assistive technology, next to top, trim and base. It holds the light for all its cubbies.
  - Only its opacity animates. No per-cubby gradient animation.
- **D-12: Box fronts get almost no light (R4).**
  - The light is strongest on the back panel and box tops, and only slightly lifts box fronts.
- **D-13: Whether the room dims in the evening is decided by sight in the mock-up round.**
  - The choice is between the wall and the cabinet's outside darkening a little in Evenings mode after dusk, and lights only.
- **D-14: If the room dims, "evening" is marked before the first paint (R6).**
  - A tiny external script in the page head reads the clock and marks evening. It is a file, not inline code, under the strict CSP.
  - The room is dark from the first frame, and the lights still fade on.

### Walls and what follows

## Summary

The phase is mostly a front-end restructuring on top of an unusually clean server seam. The finish is already one stored string (`OwnerData.Finish`) read by one singleton (`SiteFinish`) and written as a `finish-*` class on `<body>` by two layouts. Nothing caches the page: there is no output cache, and the layout JSON is keyed by collection version and profile only, so a look change never invalidates anything. The cabinet DOM is built client-side by `render.js` from `/cabinet/layout`, so the server's first paint carries the wall and chrome (from `<html>` attributes) and the sections arrive after the fetch with their reserved `aspect-ratio`. That is why a server-written attribute set gives "no flash" without any cache work.

The three hard parts are not where the UI contract spends its words. (1) **The CSS cascade:** the contract's four `@layer`s lose to every *unlayered* rule, and `site.css` declares `--wood-edge`, `--ink` and others unlayered on `:root`, which will silently beat wood-layer tokens of the same name on `<html>`. The existing block also redeclares `--wood` on every `.section > *`. Token naming and file layout must be decided up front. (2) **The stored-schema bump:** `OwnerData` is a positional record with `string Finish`, three code paths compare against `CurrentSchemaVersion`, and the very first owner save of any kind after the upgrade rewrites the file as the new version, which the previous release refuses. The plan must force an earlier-version copy at that first save. (3) **The sunset table:** a fixed table with summer-time steps baked in is wrong by an hour for up to six days per year because the change dates move; computing the table in winter time and adding the visitor's own summer-time flag gives a worst error of 0.9 minutes (computed here) and still reads "local clock times with summer time applied".

Two folded todos are independent of the look. The check-link failure is a shared singleton `IImagePacer` whose turn is held for the whole request of a slow background fetch; the owner's check waits behind it inside its own 15 s limit. Balancing the desktop sections collides with the engine's stability contract (adding a game changes at most one cubby), which needs an explicit decision before anyone codes it (Open Question 1).

**Primary recommendation:** Do the mock-up round first (scratch, owner-approved), written together with an A/B default-identity test that compares the new CSS against a frozen copy of today's stylesheets *in the same browser session* (no committed baseline images, immune to font and layout-version differences). Then split the CSS into one file per layer, add the five attributes on `<html>`, migrate the owner data to a per-field-normalised look, carry the look in the existing live status, and build `evening.js` on a smooth standard-time table plus the visitor's own summer-time flag.

### Pattern 1: A/B default identity against a frozen copy of today's stylesheets
**What:** One Playwright test loads the cabinet page twice in the same browser, same fonts, same layout JSON. Run 1 serves the new stylesheets. Run 2 intercepts `**/css/cabinet.css*` and `**/css/site.css*` and fulfils them from copies of today's files kept as test resources. Both full-page screenshots (viewport grown first, because `content-visibility: auto` leaves off-screen sections unpainted) are decoded with ImageSharp and compared with zero tolerance.
**When to use:** Written first, before the CSS split; stays as the guard that "today's look never changes" for every later change to shared structure.
**Why:** It proves identity against the *actual old release code*, removes cross-machine anti-aliasing and font differences (both renders happen on one machine), and removes the ordering constraint with the layout balancing (both sides use whatever layout the server serves). The legacy `<body class="finish-classic">` is not referenced by any rule (grep showed `finish` only in comments of `cabinet.css`), so the old CSS ignores the new markup.
**Example:**
```csharp
/// Skeleton, illustrative. Names are proposals.
await Page.RouteAsync("**/css/cabinet.css*", route => route.FulfillAsync(new() { Path = LegacyStyles.Path("cabinet.css"), ContentType = "text/css" }));
await Page.RouteAsync("**/css/site.css*", route => route.FulfillAsync(new() { Path = LegacyStyles.Path("site.css"), ContentType = "text/css" }));
```
The new split adds extra stylesheet links (`cabinet-design.css` and so on); in the legacy run abort or fulfil them empty so the old single file is the only source.

### Pattern 2: Five attributes on `<html>`, selectors on any ancestor
**What:** The server writes `data-design`, `data-wood`, `data-backs`, `data-lights`, `data-depth` on `<html>` of `_Layout` only. CSS is written `[data-wood="oak"] { ... }` (never `:root[data-wood=...]`), so the identical rules drive the Settings preview wrapper. The wood layer's base block (default = warm brown tokens) is declared with a selector that also matches an element carrying none of the attributes, per contract rule 4.
**Example:**
```cshtml
@* _Layout.cshtml, illustrative *@
<html lang="@language.Code" data-design="@Look.Design" data-wood="@Look.Wood" data-backs="@Look.Backs" data-lights="@Look.Lights" data-depth="@Look.Depth">
```
Values come from `SiteLook.Current`, already normalised per field; Razor HTML-encodes regardless.

### Pattern 3: Per-field normalisation with strings, not enums
`StrictEnumConverter` refuses any unknown enum name and would make the whole owner file unreadable, which contradicts "unknown values fall back per field". Store five strings, validate each against its own allow-list at the edges (read, restore, set, render). `Normalize(string? stored)` per field returns the value or that field's default, exactly the shape `Finishes.Normalize` has today.

### Pattern 4: Owner-data upgrade as a JSON transform before deserialisation
`OwnerDataStore.Parse` and `OwnerDataExport.Check` both call `JsonSerializer.Deserialize<OwnerData>` with required properties, so a v1 file (no `look`, has `finish`) would be reported malformed. Do the upgrade on a `JsonNode` after the header is read: when `schemaVersion` is 1, remove `finish`, add `look` with the five defaults, set `schemaVersion` to 2, then deserialise. Every v1 file holds `finish: "classic"` or an unknown string, and both restore as the five defaults. `RestoreCheck.FormatVersion` must keep reporting the file's own version, because `Settings.cshtml.cs` turns `FormatVersion < CurrentSchemaVersion` into the existing "older format, upgraded when restored" line; that plumbing already exists in `_OwnerRestorePanel.cshtml`.

### Pattern 5: Live look via the existing status channel
Add a `look` object to `CabinetStatus` (one construction site, `SyncStatusService.Current()`), have `OwnerChangeNotifier` dedupe on `SnapshotVersion + look` instead of `SnapshotVersion`, and keep the quiet period (3 s plus broadcast stays inside "about 5 seconds"). `/cabinet/status` carries it too, so a page restored from the back-forward cache or reconnecting catches up through the existing `catchUp()`. `look.js` is handed the same status as `sync.applyStatus` from `cabinet.js` and ignores statuses older than the newest `serverTimeUtc` it has seen.

### Pattern 6: `evening.js` as a classic head script with a smooth table
Shape (illustrative; no `//` comments, no regex literals containing `//`):
```javascript
/** Marks evening and lit before the first paint. */
(function () {
  var root = document.documentElement;
  /* table rows: [dayOfYear, riseMinutesStandardTime, lampOnMinutesStandardTime] */
  /* isEvening(now): standard time = now minus the visitor's own summer-time offset */
  window.cabinetEvening = { isEvening: isEvening, msToNextChange: msToNextChange };
})();
```
- The table holds **standard-time** minutes at the reference position (smooth over the year, 36 points, linear interpolation by day of year, wrapping at year end).
- The visitor's summer time comes from the visitor's own clock: `dst = now.getTimezoneOffset() < Math.max(jan.getTimezoneOffset(), jul.getTimezoneOffset())` for the current year; add 60 minutes to table values when `dst`.
- Evening when local minutes are at or after `lampOn(today)` or before `rise(today)`. Re-check on load, every 60 s while visible, on `visibilitychange`, and with one `setTimeout` to the next boundary so an open page fades at the moment.
- `look.js` (module) reads `window.cabinetEvening`; `evening.js` is the only copy of the table.

### Anti-Patterns to Avoid
- **Redeclaring tokens the unlayered `:root` already owns.** Do not use `--wood-edge`, `--ink`, `--wood-mid`, `--wood-dark`, `--wood-light`, `--wall-text` as wood-layer token names. See Pitfall 1.
- **`will-change: opacity` on every `.section-light` permanently.** One composited layer per section is allowed for the fade only; set the hint only while fading (Pitfall 9).
- **A second scroll keeper in Chromium and Firefox.** They anchor natively; set `overflow-anchor: none` only for the duration of a design change and let the script be the single keeper (Safari has no scroll anchoring [CITED: caniuse.com/mdn-css_properties_overflow-anchor], so the script is needed there).
- **Overlay above a box face.** The lamp stays under the boxes; Rust has 4.5034:1 at the 20 % shade, no room (computed).
- **Pair selectors** (`[data-design="library"][data-wood="birch"]`): a CSS test fails them.

## Common Pitfalls

### Pitfall 1: Unlayered CSS beats the new layers; same-named tokens on `<html>` lose
**What goes wrong:** `site.css` declares `--wood-edge: #8c5d38` and `--ink: #2a1a10` unlayered in `:root` [VERIFIED: site.css:5-6, quoted: `--ink: #2a1a10;` `--wood-edge: #8c5d38;`]. `<html>` also matches `[data-wood="oak"]`. Unlayered normal declarations beat layered ones regardless of specificity [CITED: developer.mozilla.org/en-US/docs/Web/CSS/@layer: "Styles that are not defined in a layer always override styles declared in named and anonymous layers"]. So an oak `--wood-edge` set in the wood layer on `<html>` is ignored, and the page stays brown.
**Why it happens:** The contract's wood token table reuses today's names (`--wood-edge`, `--ink` for ring halo and recess).
**How to avoid:** New wood-layer names that `:root` does not declare (for example `--frame`, `--frame-lit`, `--room`, `--back`, `--recess`, `--ring-halo`). Keep `--wood-dark/mid/light/edge`, `--ink`, `--wall-text`, `--chrome-*` as today's unlayered tokens for owner chrome, card and fallbacks. Also remove the per-element `--wood: var(--wood-mid)` that `.section > *` sets today [VERIFIED: cabinet.css:639, quoted: `--wood: var(--wood-mid);`], because a declaration on the element beats any inherited wood-layer `--wood`.
**Warning signs:** The oak or birch switcher changes the wall but not the frame; a `node --test` that asserts every wood-layer custom property name is absent from the `:root` blocks of the unlayered stylesheets (add it).

### Pitfall 2: Any overlay above a box face breaks Rust
**What goes wrong:** Rust (`#b8481a`, white text) is 5.28:1 bare and 4.5100 (float) / 4.5034 (8-bit rounded) under the frozen 20 % shade; Teal 4.667 / 4.691 [VERIFIED: computed here with the gamma-correct formula, shade `#140a04`]. Headroom is 0.003 to 0.01.
**How to avoid:** Keep `--lamp-front` at 0 and the lamp under the boxes (stacking map). The nine-case test must assert the tokens, not just the maths: `--lamp-front: 0`, shade alphas flat 0 / shaded 0.20 / deep 0.12, all at or below `SpinePalette.MaxShadePercent` (20) [VERIFIED: SpinePaletteTests.cs "SpinePalette.MaxShadePercent.Should().Be(20)"]. Note box colours are not always palette tones: art-derived pairs go through `SpineColour.PairFor`/`IsValidPair`, which already require 4.5:1 under the 20 % shade, so a lamp that never touches the face keeps those safe too.

### Pitfall 3: The first owner save after the upgrade rewrites the file as v2
**What goes wrong:** `OwnerDataStore.Parse` returns `Unreadable("newer format")` when `known.SchemaVersion > OwnerData.CurrentSchemaVersion` [VERIFIED: OwnerDataStore.cs:155-158]. After the schema bump, the previous release cannot read any file the new one saved. The new release saves on *any* owner change (a location move, a picture choice), not only a look change, so a rollback after a trivial edit already falls back. `KeepEarlierVersionWhenDue` only copies when the newest copy is older than an hour [VERIFIED: OwnerDataService.cs:453-460, quoted: `now - newest > VersionInterval`], so the v1 file may not be preserved.
**How to avoid:** When the stored file's version is below `CurrentSchemaVersion`, keep an earlier-version copy before the first v2 save regardless of the interval (copy the bytes, they are v1). Test it. State the rollback behaviour in the plan: a rollback after any v2 save lands on the kept v1 copy through the existing recovery panel, or on defaults.
**Warning signs:** `owner-data-versions/` has no v1 file after the first post-upgrade save.

### Pitfall 4: Fixed summer-time dates in the table, and no longitude
**What goes wrong:** EU summer time changes on the last Sunday of March and October, a different date each year (2027: 28 Mar and 31 Oct). A table of local clock times with the step baked in at one year's dates is wrong by an hour for up to six days a year. Computed worst error across the year with 3 points per month and the 2027 steps: **49 minutes**. Also local clock sunset depends on longitude (4 minutes per degree, computed), and the contract fixes only a latitude.
**How to avoid:** Table in standard time at a fixed latitude and longitude (START: 52 N, 5 E [ASSUMED], the table's longitude is the only number the contract leaves open); add 60 minutes from the visitor's own summer-time flag. Computed: worst error **0.86 minutes** (12/27) against the solar formula for 2027, 0.93 minutes for the same table against 2030, with 36 points and linear interpolation. This stays inside "local clock times with summer time already applied" and follows each year's real change date for any visitor whose zone uses summer time. The unit test compares the table with an independent C# solar implementation for several years within 5 minutes, and tests the flag with injected `getTimezoneOffset` values.
**Anchors for the executor (computed, NOAA, 52 N 5 E, local clock with summer time):** 21 Dec rise 08:46, sunset 16:30; 21 Jun rise 05:20, sunset 22:04; lamp on 30 minutes before sunset. [VERIFIED: computed in this session]

### Pitfall 5: The notifier and tests assume only collection changes are news
**What goes wrong:** `OwnerChangeNotifier.AnnounceAsync` returns early when `status.SnapshotVersion == _lastSentVersion`, so a look-only change publishes nothing; `CollectionPublisher.Replace` also returns false (version unchanged). Existing test "A burst that ends where it began notifies nobody" must stay true for looks too.
**How to avoid:** Dedupe on a composite key; keep the per-burst quiet period. Three tests construct `SyncStatusService` directly (`SyncWorkerTests`, `SampleGenerationTests`, `OwnerChangeNotifierTests`), so make the look source an optional constructor argument.

### Pitfall 6: Existing CSS tests pin literals the split will move
**What goes wrong:** `build/tests/cabinet-css.test.mjs` asserts the exact text `calc(-1 * var(--lw)) calc(-1 * var(--lw)) 0 0 rgb(255 235 210 / var(--arch-lit))` and `--lw: max(1px, calc(0.8 * var(--u)))`. Moving tints into tokens (`rgb(var(--arch-light-rgb) / var(--arch-lit))`) breaks it by design. It also asserts that no variable carries a hard-coded colour fallback.
**How to avoid:** Update that test in the same task as the split, asserting the new tokenised form and that the token's value is `255 235 210` in the wood layer. The default-identity A/B is the real proof; the text tests only guard shape.

### Pitfall 7: Owner pages and the owner-address cabinet use different layouts
**What goes wrong:** `Pages/_ViewStart.cshtml` sets `_Layout`; `Pages/Owner/_ViewStart.cshtml` sets `_OwnerLayout` [VERIFIED: read both]. The cabinet at the owner address uses `_Layout` and gets the attributes (contract: yes). Owner pages use `_OwnerLayout` and must carry none. The shared `_Footer` renders on both and must show the white logo when there are no attributes.
**How to avoid:** Pass the logo choice as a footer model/ViewData from each layout; test both ports on every page path (the existing `FinishSlotTests` loop over `OwnerPagePaths` is the pattern).

### Pitfall 8: The Settings page loads neither the cabinet CSS nor `render.js`
**What goes wrong:** `_OwnerLayout` links only `site.css` and `owner.css`. The preview "runs the real cabinet code", so it needs the four layer files, `render.js` (public), the English `copy.js` strings, and a sample layout.
**How to avoid:** Add a `Head` section to `Settings.cshtml` (the layout already renders `RenderSectionAsync("Head")`). Prefer a hand-authored synthetic layout JSON for the preview (two rows of three cubbies, invented titles, one face-out cover, one empty cubby) served owner-only, for example as `wwwroot/js/owner-look-sample.json` which the `js/owner-` prefix rule makes owner-only for free, validated by a test against the `LayoutJson` shape. Do not derive it from `CabinetLayoutEngine`: it would then churn with every `LayoutVersion` bump (the balancing). A JSON data block inside the page would work under the CSP too, but the contract says never inline script, and a fetched file keeps the page test "no inline script bodies" simple.

### Pitfall 9: Composited layers per section on a phone
**What goes wrong:** One `section-light` per section is fine, but a permanent `will-change: opacity` on all of them can keep many large layers alive. [ASSUMED: browser layer-promotion behaviour]
**How to avoid:** `content-visibility: auto` already unpaints off-screen sections. Set the hint only while the fade runs (a `data-fading` state) or rely on the browser promoting during the transition; measure with the non-gating frame check.

### Pitfall 10: The pull-out's view-transition CSS targets the root group
**What goes wrong:** `card.css` sets `::view-transition-group(root), (pull), (card) { animation-duration: var(--pull-dur) }` [VERIFIED: card.css:654-658]. A look switch that calls `startViewTransition` inherits 350 ms, not the contract's 250 ms.
**How to avoid:** Mark the look switch with an attribute (for example `html[data-look-switch]`) and give it its own `::view-transition-group(root)` duration; never start it while `html[data-pull-kind]` or `[data-pulling]` exists (the contract already defers a look change until the animation ends). Remember a new `startViewTransition` skips a running one.

### Pitfall 11: Browser geometry and pixel tests are font- and viewport-sensitive
**What goes wrong:** CI draws `system-ui` as a wider font; `content-visibility: auto` leaves off-screen sections empty in plain full-page screenshots; rows return empty `innerText` off-screen.
**How to avoid:** Run with the DejaVu fontconfig (below) before pushing; grow the viewport to the document height before screenshots (the senior-frontend `shoot.mjs` does it); scroll a section into view before reading its edge pixels; use retrying `Expect(...)` assertions; assert geometry relative to measured values.

### Pitfall 12: WebKit is not installed in CI or locally
**What goes wrong:** The contract wants the live place-keeping test in Chromium and WebKit. CI installs only `chromium-headless-shell` [VERIFIED: ci.yml browser-tests job]; the local Playwright cache has only `chromium_headless_shell-1243`.
**How to avoid:** Decide the scope (Open Question 4). Recommended: keep the scroll-keeper logic unit-tested in Node with stubs, run the one real WebKit test in its own CI step after `playwright install --with-deps webkit`, and launch WebKit explicitly in that test (`Playwright.CreateAsync()` then `Webkit.LaunchAsync`) instead of depending on a runner argument for `BrowserName` (the docs show a `runsettings`/CLI property but do not cover xUnit v3 on the Testing Platform runner [CITED: playwright.dev/dotnet/docs/test-runners], [ASSUMED] for MTP).

### Pitfall 13: Repo lint rules bite new files
**What goes wrong:** A `//` anywhere in JS (including `'//'` or a regex), a planning word in a test name or CSS comment, or a `/* */` that does not open with `/**` fails `build/lint.sh`.
**How to avoid:** Write doc blocks only; keep decision IDs and phase words in `.planning/` only; name tests after behaviour.

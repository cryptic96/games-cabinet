# Phase 06.1 Plan 09: Older data survives, a rollback finds its copy, and publishing follows the owner-page rules Summary

A release that bumps the owner-data format now keeps a byte-identical copy of the old file before its first save (any save path, inside the hour or not), so a rollback lands on that copy through the existing recovery panel; every allowed look value round-trips through download and restore, and publishing a look has an Undo that takes the look and its log entry back.

## What was built

- `IOwnerDataStore.StoredSchemaVersion()`: the schema version in the header of the file on disk, or null without a file or with an unreadable header. `OwnerDataStore` reads only the header and never writes; the in-memory test store tracks a seeded or last-stored version; `SometimesFailingStore` delegates.
- `OwnerDataService.KeepEarlierVersionWhenDue` also copies when `StoredSchemaVersion()` is below `OwnerData.CurrentSchemaVersion`. It is called by `MutateAsync`, `UndoAsync`, `MutateSystemAsync` (the sync's thirty-day reconcile) and `RecordDownloadAsync`; `RestoreAsync` already always copied. After the first save the file is current, so the hourly rule applies again.
- `docs/deploy.md`: "the cabinet look" replaces "the cabinet finish"; the earlier-versions list names the format-change copy; a new subsection "Rolling back after a format change" says the previous release cannot read the new file, the recovery panel opens, the pre-upgrade copy is restored from the earlier versions, and the look returns to the default.
- Settings: `OnPostUndoAsync(revision)` through `OwnerResponses.For`, `LookUndoRevision` (set after a saved publish), a no-script `Undo` form under the status line, and look wordings in `OwnerStrings` (`look-set` now reads the saved-for-everyone line, plus undone, out-of-date and failed-save lines).

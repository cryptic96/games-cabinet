# Plan 06.1-04: Balanced desktop sections - the prototype, the numbers and the owner's choice of promise

## Phase Goal

ROADMAP goal (not yet in user-story form; flagged, see `/gsd mvp-phase 6.1`): "From the owner pages, the owner picks the cabinet's finish for every visitor from seven furniture looks, each with its own wall, and switches warm cubby lighting on, optionally only at night by each visitor's own clock, plus a cubby-depth look." This plan carries the folded layout todo (CONTEXT D-34) so every design reads as a full piece of furniture.

Coverage note: no SPEC; the spec-less probe fallback was skipped visibly; no probe-derived Edge Coverage or Prohibition predicates exist for this run.

<objective>
Owner decision P1-A: prototype the even spread on the 65 and 400 samples first, measure how many games move when one game is added, show before and after desktop sheets, and let the owner choose the new stability promise at a blocking checkpoint. The prototype is production-quality engine code behind a layout switch that is off by default, so nothing visible or recorded changes until the owner has chosen (the switch is turned on, the promise rewritten and the version bumped in plan 06.1-05).

Purpose: balancing collides with today's promise that adding a game changes only the cubby it lands in (`FamilyStabilityTests`, `docs/cabinet-layout.md` "Stability"); that promise is changed on purpose, by the owner, with evidence.
Output: the balancing pass behind `Layout:BalanceSections`, its tests, sheets and numbers in `06.1-BALANCING-REVIEW.md`, and the owner's answer.
</objective>

    - With `BalanceSections` on, every phone layout of samples 0, 1, 5, 12, 65 and 400 is equal to the phone layout with it off.
    - With `BalanceSections` off (the default), `LayoutOptions.Default.Fingerprint` and every golden layout are unchanged (`LayoutGoldenTests` passes untouched).
    - `Layout:BalanceSections` reads `true` and `false`, defaults to off when absent, and a present blank or non-boolean value stops startup with a message naming the key.
  </behavior>
  <action>
1. Tests first (`[Trait("Category", "Layout")]`, names describe behaviour).
2. `LayoutOptions`: add a trailing `bool BalanceSections = false` with a `///` param doc; pack it into `Fingerprint` with a new shift so that `false` contributes nothing (the existing fingerprints, and so the goldens, stay byte-identical).
3. `SectionDesign`: add an init property (for example `BalancesSections`, default false, `///` summary: whether this design spreads its games evenly over its sections when the option asks for it); set it on `SectionDesigns.Desktop` only. The phone design never balances.
4. `CabinetLayoutEngine`: when both are on, spread the games so the drawn sections come out about the same height. Suggested method (a reversible implementation choice): keep today's greedy placement to learn the section count N; then find the smallest per-section row budget R for which placing the same games in the same reading order, with each section allowed to use only its first R shelf rows, still needs no more than N sections; place with that budget; draw every section down to its last used row (never fewer than `MinTrimmedRows`). Keep the engine pure and deterministic; keep every existing rule (series together, families, lie-flat before a new section) inside the budget. Update the engine's class summary for the option only; the version stays 15 here.
5. `LayoutSettings`: read `Layout:BalanceSections` with `ReadSwitch`, default `LayoutOptions.Default.BalanceSections`; update the "seven Layout keys" summary to eight.

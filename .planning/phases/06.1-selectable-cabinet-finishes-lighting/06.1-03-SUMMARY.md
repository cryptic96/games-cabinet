# Phase 06.1 Plan 03: Your own "Check link" never waits behind the background worker Summary

The owner's interactive Check link now runs on a fetch slot of its own (own pacer, own credential-free picture client, own fetcher), so a working link is previewed at once even while the background link worker is held on a slow one.

## What was built

- `OwnerCheckFetcher.cs` (new): `IOwnerCheckPacer`, `OwnerCheckPacer` (an `ImagePacer` with the configured gap on its own state) and `OwnerCheckFetcher`, a thin holder of an `OwnerLinkFetcher` built on that slot.
- `OwnerEndpoints.AddOwnerCheckSlot`: registers the pacer, a named `owner-check` HTTP client configured like the art client (same timeout, same buffer limit, `BggTransport.CreatePrimaryHandler`, no auth handler) and the fetcher. The fetcher builds a new `ImageDownloader` per check from that client, the same `ArtSourcePolicy`/`ArtLimits` and the owner-check pacer.
- `PicturesModel` takes `OwnerCheckFetcher`; `OwnerLinkWorker` is unchanged and still resolves the shared `IArtSource`, so the shared `AddHttpClient<IArtSource, ImageDownloader>` registration (one occurrence) and the shared `IImagePacer` are untouched.
- Doc comment on `OwnerLinkFetcher` reworded to say there is one fetcher per slot.
- `docs/bgg-sync.md`: the pictures list and the `Images__DownloadGapMilliseconds` row now say the gap applies per slot, that background work shares one slot, that the owner's check has a second one, and that at most two picture requests can overlap.

## Tests

- `OwnerCheckLinkSlotTests` (integration): a link the worker holds on a slow address while another game's link is checked; the check answers `ready` before the slow request is released, with no authorization header and no cookie, and the worker then finishes its own game. A second test proves two checks in a row are spaced by the gap on the fake clock (nothing requested before the clock moves, then served).
- `OwnerCheckSlotTests` (unit): each pacer keeps the gap, a held turn on either slot never delays the other, and a second turn on the shared slot waits while the first is held (the worker and the sync never overlap).
- Red run recorded for the tracer: with the owner check still on the shared slot, the test failed with "Expected finished to refer to the check task ... but found the 10 s delay" (the check was waiting behind the held turn). After the change it passes in about 1 s.
- Results: `OwnerCheckLinkSlotTests` 2/2, `OwnerCheckSlotTests` 5/5, `OwnerLinkFetcherTests` 33/33, `OwnerLinkTests` 6/6, `OwnerLinkPreviewTests` 27/27, whole integration project 454/454, repository lint passes, browser test project builds.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `SyncHarness.CreateFactory` could not give a test a real shared pacer**
- **Found during:** Task 1 (writing the red test).
- **Issue:** The harness always registers a pacer that never waits for the shared slot, so no test could reproduce a check waiting behind the worker.
- **Fix:** Added an optional `configureServices` argument that runs after the defaults; the tests register a real `ImagePacer` on the fake clock for the shared slot.
- **Files modified:** `Cabinet.IntegrationTests/Infrastructure/SyncHarness.cs`
- **Commit:** 8649915

**2. [Rule 3 - Blocking] The harness needed a default pacer for the new slot**
- **Found during:** Task 1.
- **Issue:** A real owner-check pacer on the fake clock would hang every existing test that checks two links in a row.
- **Fix:** `NoWaitPacer` also implements `IOwnerCheckPacer` and the harness registers it by default; the slot tests register a real `OwnerCheckPacer`.
- **Files modified:** `Cabinet.IntegrationTests/Infrastructure/NoWaitPacer.cs`, `SyncHarness.cs`
- **Commit:** 8649915

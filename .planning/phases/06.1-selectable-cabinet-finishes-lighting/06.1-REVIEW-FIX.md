## Fixed Issues

### WR-01: A stored file with `schemaVersion` of 0 or below is no longer rejected

**Files modified:** `Cabinet.Repository/Storage/OwnerDataStore.cs`, `Cabinet.UnitTests/Owner/OwnerDataUpgradeTests.cs`
**Commit:** b816245
**Applied fix:** `Parse` now returns unreadable for a header version below 1 before any upgrade, the same rule `OwnerDataExport.Check` uses; the dead post-upgrade check was dropped. Tests for versions 0 and -5 assert the file is unreadable and left byte for byte as it was.

### WR-03: The rollback copy can be overwritten or pruned

**Files modified:** `Cabinet.Repository/Storage/OwnerDataStore.cs`, `Cabinet.Domain/Owner/OwnerData.cs`, `Cabinet.UnitTests/Owner/OwnerDataStoreTests.cs`, `Cabinet.UnitTests/Owner/OwnerDataServiceTests.cs`
**Commit:** 5de494e
**Applied fix:** `KeepEarlierVersion` now detects a file whose header names a format from 1 up to below the current one and writes it as `owner-data.format-<n>.<millisecond stamp>.json`. That name is never replaced (a taken name moves on by one millisecond), is excluded from the ten-copy pruning, is skipped when a byte-identical copy exists, and is still listed, read and restored through the same earlier-versions listing. Tests cover the dedicated name, a same-second later copy, survival past more than ten later copies, no duplicate for an unchanged file, and the ordinary name for a current-format file. Three existing service tests that pre-seeded a recent copy from the old-format file itself now seed an unrelated recent copy.

### WR-04: Restoring a format-1 backup silently resets the look

**Files modified:** `Cabinet.Service/Owner/OwnerStrings.cs`, `Cabinet.UnitTests/Owner/OwnerStringsTests.cs`, `Cabinet.IntegrationTests/OwnerBackupTests.cs`
**Commit:** 20996ea
**Applied fix:** The restore preview line for a first-format file now also says "It holds no look, so the cabinet is restored with the default look." (English only, as all owner pages). Unit tests cover the string for format 1 and format 2; the integration test of a restored first-format file asserts the line in the preview. Behaviour (restore uses the default look) is unchanged, as decided.

### WR-05: Overlapping look applications can leave an older look on screen

**Files modified:** `Cabinet.Service/wwwroot/js/look-switch.js`, `build/tests/look-switch.test.mjs`
**Commit:** 4fe5cf8
**Applied fix:** Each accepted look gets a rank per root; a look writes only while it is still the newest one asked for. The rank is re-checked after `await loadEveningScript` and inside the cross-fade update callback (and a look held during a pull-out carries its rank). Node tests: an older look waiting for the evening script does not overwrite a newer applied look; a newer look reverting to the page's state cancels an older look pending in a cross-fade; two cross-fades in flight write only the newer; a late older status is still ignored. The first three fail when the check is disabled.

### WR-06: `TryAdmit` rejects an already admitted id at the cap; `IsAdmitted` has no production caller

**Files modified:** `Cabinet.Service/Live/LiveConnectionLimiter.cs`, `Cabinet.UnitTests/Live/LiveSettingsTests.cs`
**Commit:** f966c93
**Applied fix:** Admission is now one lock over a set of ids: an admitted id is admitted again without a second place, a new id is admitted only below the cap, and the cap is exact under concurrent attempts. `IsAdmitted` stays and its `///` summary states that only the tests that wait for admission call it. Tests cover the repeat at the cap and 200 concurrent attempts against a cap of 20; the live hub and cap-refusal integration tests still pass.

### WR-02: The forced rollback copy can fail silently and the save then overwrites the old-format file anyway

**Files modified:** `Cabinet.Service/Owner/OwnerDataService.cs`, `Cabinet.UnitTests/Owner/OwnerDataServiceTests.cs`, `docs/deploy.md`
**Commits:** f5e1a2d (log message), a49f4b4 (refusal)
**Owner decision changed:** the build review first decided that a failed forced copy must not stop the save, and the log message was reworded under that decision (f5e1a2d). After the security audit found the data-loss-on-rollback threat still open, the decision changed to refuse the save, which a49f4b4 implements.
**Applied fix:** While the stored file is in an older format, a failed copy (`IOException` or `UnauthorizedAccessException`) is rethrown by `KeepEarlierVersionWhenDue`, so the callers' existing catch answers refused with `save-failed` (owner change and undo), skips the write (the sync's write) or records no download. The old file is never overwritten without its copy. A failed routine copy of a file already in the current format is still logged and the save continues. Restore already refused on any failed copy. Tests (real store, versions folder blocked by a plain file) cover owner change, undo, sync write and download record, asserting the format-1 file is byte for byte untouched, that writes go ahead once the copy works, and that a current-format file still saves when its routine copy fails. `docs/deploy.md` now describes the dedicated never-replaced copy and the refusal.

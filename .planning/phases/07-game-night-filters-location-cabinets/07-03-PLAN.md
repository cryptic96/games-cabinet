# Plan 07-03: Each copy of a game gets its own place - the owner-data format gate and the per-copy data

## Phase Goal

ROADMAP goal (not yet in user-story form; flagged, see `/gsd mvp-phase 7`): "A visitor can narrow the cabinet to tonight's game by dimming everything else, and can switch between one big cabinet and one cabinet per storage location."

Coverage note: no SPEC; spec-less probe fallback ran (see plan 07-01 for the totals). This plan carries the owner-data prohibition. Folded todo: owner pages collapse owned versions of one game (the Locations page rows follow in plan 07-08, the Pictures page rows in plan 07-16, which closes the todo).

<assumption_delta_decision>
Noun now primary: the collection entry (one copy of a game), `CollectionId`.
Decision (recommended, confirmed at the gate in Task 1): add-alongside. `OwnerGame` keeps `GameId` and gains `CollectionId` as an optional trailing member; null means "every copy of this game", which is the form every schema-1 and schema-2 file has. Rationale: the upgrade step runs on bytes with no synced collection at hand, so it cannot know a game's copies; keeping the game-wide form lets older files load unchanged, and the first edit of any copy splits it into per-copy entries. Every per-copy edit writes per-copy entries, so the per-copy key is the one the owner's actions produce.
Accepted debt: game-wide entries can live on indefinitely for games the owner never edits again, so the reading rule (copy entry, else game-wide entry) stays in `OwnerGames.Find` and `OwnerOverlay`; the game-level edit signatures (`LocationEdits.Assign(data, gameId, ...)` and, in plan 07-13, the picture edits) stay as the "every copy of this game" form that test seeding and single-copy games use, while the owner pages call only the per-copy forms. What would force a later promote: a future schema step that runs with the synced collection at hand (or the owner choosing option-b at the gate), after which every entry carries a collection id and `GameId` becomes a descriptive field only. If the owner chooses option-b at the gate, this decision is recorded as promote instead, and execution stops until this plan and plans 07-08, 07-09, 07-13, 07-18 and 07-20 are revised through `/gsd-plan-phase`.
Invariant test (added, Task 3): every per-copy choice round-trips save, download, restore and the public card, for a game owned once and a game owned three times, including a game-wide entry from an older file.
</assumption_delta_decision>

<objective>
Gate the one-way owner-data format step with the owner (D-31 reversibility), then build the thinnest end-to-end path of per-copy owner choices below the owner pages: schema 3 with a collection id on each owner entry, the overlay resolving locations per copy, a per-copy edit that splits a game-wide entry first, and each copy's own location reaching its public card (LOC-01) and therefore the location filter and cabinets later (FILT-04, LOC-05). Finally pin the upgrade, rollback copy, restore pair checks and the round-trip invariant with tests. The Locations page moves to per-copy rows in plan 07-08.

Purpose: a game owned in several versions can stand in two places, and the cabinet, the filter and the location cabinets will treat each copy as the box it is.
Output: schema 3, `OwnerGames`, the per-copy overlay and edit, the storage chain and pair checks, round-trip and storage tests.
</objective>

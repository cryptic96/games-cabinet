# Plan 07-07: The keyboard follows the light

## Phase Goal

ROADMAP goal (not yet in user-story form; flagged, see `/gsd mvp-phase 7`): "A visitor can narrow the cabinet to tonight's game by dimming everything else, and can switch between one big cabinet and one cabinet per storage location."

Coverage note: no SPEC; spec-less probe fallback ran (see plan 07-01). This plan lifts no probe edge; it implements D-20's keyboard rules.

<objective>
Make the cabinet's roving keyboard model follow the filter (D-20, R8): arrows, Home and End move only between matches, Tab enters on a match, the tab stop leaves a box that falls into shadow, and nothing traps a keyboard user when nothing matches.

Purpose: a keyboard user filters and walks straight through the answers.
Output: lit-aware `keys.js`, node tests for the pure parts, `FilterKeyboardTests`.
</objective>

    - browser (`FilterKeyboardTests.Tab_enters_the_cabinet_on_the_first_match`): with nothing focused yet, typing a query and pressing Tab from the search field (through the remaining bar controls) lands on the first lit box in on-screen reading order (rectangles sorted by top, then left); the same holds after typing one more letter without entering the cabinet, and on a page where the visitor had first moved the stop with the arrow keys and then started the filter from the search field.
    - browser (`FilterKeyboardTests.The_tab_stop_leaves_a_box_that_falls_into_shadow`): after the visitor has focused a lit match and moved focus back to the search field, a query change that dims that box leaves exactly one box with `tabindex="0"`, the lit box nearest to the old holder; a query change that keeps it lit leaves the stop on it. When the holder has focus and a filter change dims it (applied without moving focus: a page script sets `#filter-q`'s value and dispatches `input`), it loses `tabindex="0"` to the nearest lit box while `document.activeElement` stays on it, and the next arrow moves to a lit box.
    - browser (`FilterKeyboardTests.Zero_matches_and_Clear_restore_every_box_to_the_arrows`): with a query that matches nothing, arrows move over every box; after Clear, arrows again move over every box and the tab stop stays where it was.
    - browser (`FilterKeyboardTests.Enter_on_a_box_in_shadow_opens_its_card`): Enter on a focused dimmed box opens its card.
  </behavior>
  <action>
1. `initRoving`: listen to `cabinet:filtered` on `mount.ownerDocument` and keep one flag, "placed by the visitor": it becomes true when a box receives focus (the existing `focusin` handler) and is reset to false when a filter starts (an event with `active` true after one with `active` false, or the first event after load when it is already active); a box that has focus when an event arrives counts as placed by the visitor. On each event while at least one box is lit and at least one is dimmed: (a) when the stop is on its default (the flag is false), give it to the first lit box in on-screen reading order (the first index of `readingOrder` over the lit boxes' rectangles, sorted by top, then left, as in Task 1; not DOM order, and the same box Home goes to), so Tab enters the cabinet on the first match; (b) when the flag is true and the holder has become dimmed by this change, give the stop to `nearestBox` among the lit boxes measured from the holder's rectangle, whether or not the holder has focus, and leave focus where it is (a focused dimmed holder keeps focus; only `tabindex="0"` moves); (c) when the flag is true and the holder is still lit, leave the stop. With zero matches or no filter active, leave the stop where it is. There is no separate "no remembered key" case: `refresh()` always keeps a key after a draw, so rule (a) is what puts the stop on the first match. `refresh()` after a redraw applies the same rules with the current filter result, so a redraw while filtering never leaves the stop on a box in shadow.
2. Keep one `tabindex="0"` at all times; no `aria-disabled` and no change to the boxes' names.
3. Tests as in the behaviour list; run the repository lint.
  </action>

# Plan 08-05: Live-channel caps per client and an origin allow-list

## Phase Goal

ROADMAP goal (not yet in user-story form; flagged, see `/gsd mvp-phase 8`): "The site is reachable from the internet over HTTPS through the existing reverse proxy, resilient to traffic floods and unable to starve the other guests on the host, and the owner opens it only after a go-public checklist passes."

Coverage note: this plan lifts SEC-02 boundary for the live channel and two prohibitions. Design choice within D-04 (Claude's discretion, research Open Question 1): the origin allow-list is "the `Origin` must name the same host and port as the request's `Host`", and host filtering (plan 08-07, `AllowedHosts` from the server env file) restricts `Host` to the public and owner hostnames, so the allowed origins come from the env file with no second list that could drift. The negotiate-only window (rather than a window over every hub request) is a refinement of the research's chained policy: the Server-Sent Events transport posts every client message, including a ping every 15 seconds, so a window over all hub requests would refuse a group of fallback pages within a minute.

<objective>
Add the live channel's per-client walls (D-01, D-04): a named rate-limit policy on the hub (per-address concurrency on the long-lived connect requests, a per-address window on negotiate, nothing on Server-Sent Events message posts), an origin guard that runs before the limiter, tests for every limit on both transports and both ports, a browser test that a refused page stays quiet (D-03), and the closure of AR-03-02 and AR-03-03.

Purpose: a third-party page or one address cannot take the live places a game night needs, and each limit is proven.
Output: `LiveConnectPolicy`, `LiveOriginGuard`, new `ClientLimits` keys, `LiveAddressCapTests`, `LiveOriginTests`, `LiveRefusalTests`, the risk register updated.
</objective>
